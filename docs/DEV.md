## Ф1: установка для разработки

Пакет `pult` (демон `pultd` + CLI `pult`) собирается из TypeScript в `dist/`. Рантайм-зависимостей ноль,
devDependencies — только `typescript` и `@types/node`. Нужен Node >= 22.

```sh
npm ci
npm run build                 # tsc -> dist (продукт) и dist-test (тесты)
npm test                      # node --test по собранным тестам
PULT_HOME=$(mktemp -d) node dist/cli/main.js doctor
```

Всё состояние живёт в `PULT_HOME` (по умолчанию `~/.pult`): `run/{pultd.sock,token,pultd.lock}`,
`events/*.jsonl`, `logs/pultd.log`, `config.json`. Пока идёт разработка, запускай с временным
`PULT_HOME`, чтобы не смешивать с боевым. Глаголы В1: `daemon start|status|stop|logs`, `events tail`,
`doctor`. Глаголы В2 — ниже, служба (`daemon install|uninstall`, В4) — в разделе «Служба»,
версии (`update`, В4) и `install.sh` — в разделе «Обновление».

Демон поднимается по требованию: любая команда, которой он нужен, запускает `pultd` отсоединённым,
и он переживает закрытие терминала. Остановка — `pult daemon stop`.

## Ф1 В2: агенты Claude

Пять команд, которых хватает на полный круг работы с агентом:

```sh
pult agent start w --kind claude --cwd ~/проект --model haiku --effort low   # завести агента
pult agent prompt w "почини тест" --wait                                     # реплика и ждать ответ
pult agent read w                                                            # что модель сказала
pult perm list                                                               # что ждёт твоего решения
pult perm approve p1-3fa9c2        # или: pult perm deny p1-3fa9c2 --reason "не трогай прод"
```

Рядом: `pult agent list|wait|stop|rm|tree`, `pult usage [--json]`, `pult provider reset claude`.

- **Режим по умолчанию — процесс на ход.** Каждая реплика поднимает свой `claude` и возобновляет
  разговор через `--resume <uuid>`. Это проще, переживает обрывы сети и не держит десятки процессов.
  `--warm` оставляет процесс живым между репликами (выигрыш 1–2 с на реплику, жнец снимает его через
  `warmTtlMs`, по умолчанию 20 минут). Кэш промпта живёт на стороне API, так что тёплый процесс
  экономит секунды, а не токены.
- **Разрешения.** Всё, на что `claude` спрашивает разрешение, попадает в `pult perm list` и ждёт
  человека. Если демон недоступен или никто не ответил за `permTimeoutMs` (10 минут) — ОТКАЗ:
  недоступный хозяин не означает «разрешаю». Нода без брокера запускается с `--permission-prompts none`.
- **Страж страны выхода** стоит перед первым ходом сессии, перед любым ходом после простоя дольше
  60 с и перед первым ходом после смены правила (0.3.6). Страна из списка-стража (в режиме allow — НЕ из списка) или
  неизвестна → ход не запускается, событие `net.blocked`, код выхода 4. Правило — раздел «Страж сети» ниже.
- **Коды выхода** `pult agent prompt --wait`: 0 готово · 2 таймаут · 3 ждёт человека · 4 сеть
  заблокирована стражем · 5 провайдер недоступен.
- **`pult agent tree`** рисует субагентов и вызовы инструментов отступами; `pult usage` показывает оба
  окна лимита подписки (5 часов и 7 дней) из события `rate_limit_event`.
- **Дымовой прогон на настоящем CLI** — `npm run smoke:claude` (haiku, low, временный `PULT_HOME`,
  одноразовый git-репозиторий, страж выхода). В CI не входит.

Фикстуры сырых потоков настоящего `claude` и их описание — `test/fixtures/claude/README.md`;
перезаписываются командой `node scripts/record-claude-fixtures.mjs`.

## Ф1 В3: агенты Codex

Те же глаголы, другой провайдер — меняется только `--kind`:

```sh
pult agent start c --kind codex --cwd ~/проект --effort low
pult agent prompt c "почини тест" --wait
pult agent tree c            # субагенты Codex тоже видны
pult provider reset codex    # снять остановку провайдера
```

- **Один `codex app-server` на ВСЕХ агентов.** Общий демон Codex на машине владельца недоступен
  в принципе (бинарь живёт внутри ChatGPT.app), поэтому `pultd` держит свой процесс на stdio и
  перезапускает его. Сессии внутри — треды: два агента Codex идут параллельно в одном процессе,
  `pult agent stop` снимает ХОД (`turn/interrupt`), а не сервер. Процесс гасит только остановка демона.
  Флаг `--warm` для Codex смысла не имеет: процесс и так один на всех и живёт между репликами.
- **Тред становится возобновляемым только после первого хода.** ИЗМЕРЕНО 21.09.2026:
  после `thread/start` записи разговора на диске ещё нет, и свежий app-server отвечает
  `no rollout found for thread id …`. Поэтому `providerSessionId` попадает в реестр по первому
  `turn/started`, а на эту ошибку адаптер отвечает самолечением — заводит новый тред в том же ходе.
  Рестарт демона разговор переживает: следующая реплика идёт через `thread/resume` с `excludeTurns`.
- **Разрешения** приходят запросом JSON-RPC от сервера и отвечаются по его id. Спрашивает codex тогда,
  когда команда лезет ЗА пределы рабочей папки (измерено на живом CLI 22.09.2026). Отказ — `decline`:
  он отказывает ровно в одном действии, не обрывая ход, и принимается сервером, даже когда его нет в
  `availableDecisions`. Разрешение отправляется, только если метод его предлагает: у запроса на КОМАНДУ
  список решений приходит полем `availableDecisions`, а у запроса на ПРАВКУ ФАЙЛА такого поля в протоколе
  нет вовсе — там берётся словарь решений самого метода (`accept | acceptForSession | decline | cancel`). Стоячие
  разрешения (`acceptForSession`, поправки execpolicy и сети) — с M8d и только по явной кнопке человека (раздел
  M8d ниже); по умолчанию «да» — один раз. Молчание, остановка демона, падение
  app-server, `agent stop` и `agent rm` — ОТКАЗ, и вопрос уходит из Inbox.
- **Лимиты** читаются раз на соединение и дальше сливаются из разреженных обновлений:
  отсутствующее поле не стирает известное, а `rateLimitReachedType: null` СНИМАЕТ лимит.
  `pult usage` показывает те же два окна, что и у Claude. Кредит сброса лимита Пульт не тратит
  никогда — это решение человека.
- **Падение app-server** честно хоронит идущие ходы (`provider_unavailable`), процесс поднимается
  заново на следующей реплике; больше трёх перезапусков за минуту — провайдер остановлен, снимает
  `pult provider reset codex`. Смерть и подъём общего процесса — даже в простое — пишутся в журнал
  событием `provider.restarted` (pid, код, сигнал, счётчик перезапусков).
- **Коды выхода** те же, что у Claude; исчерпанный лимит подписки — код 5, а текст провайдера
  (`You've hit your usage limit…`) печатается на stderr.
- **Дрейф протокола.** `pult doctor` сверяет sha256 набора схем (`codex app-server
  generate-json-schema`) со слепком в `src/adapters/codex/schema.ts`. Расхождение — предупреждение,
  а не отказ работать: бинарь `codex` меняется с каждым обновлением ChatGPT.app.
- **Дымовой прогон на настоящем CLI** — `npm run smoke:codex` (усилие low, временный `PULT_HOME`,
  одноразовые git-репозитории, страж выхода). В CI не входит.
- **Бинарь переехал (ChatGPT.app 26.924, 27.09.2026).** `codex` теперь лежит в
  `/Applications/ChatGPT.app/Contents/Resources/codex-cli/bin/codex` (было `…/Resources/codex`). Поиск знает обе
  раскладки, новую первой; повисший `~/.local/bin/codex` проваливается дальше, а не теряет codex. Слепки схемы — по
  папке на версию (`spike/codex/schema/<версия>/{plain,experimental}`), сверка двух слепков для адаптера —
  `node scripts/diff-codex-schema.mjs <старая> <новая>` (выход 1, если пропал метод, который адаптер зовёт).

Фикстуры сырого протокола и их происхождение — `test/fixtures/codex/README.md`; перезаписываются
`node scripts/record-codex-fixtures.mjs` (а `--probe` снимает часть из них вообще без ходов модели).

## Ф1 В4: служба

Без службы демон живёт, пока его не остановят или не перезагрузят машину, и поднимается первой же
командой. Служба (launchd на macOS, `systemd --user` на Linux) держит его сама и поднимает после
перезагрузки и входа.

```sh
pult daemon install --dev     # из этой рабочей копии: current -> versions/<v>-dev -> корень пакета
pult daemon install           # когда активная версия уже стоит (pult update --from <tgz>)
pult daemon install --print   # показать файл службы и команды загрузки, ничего не записывая
pult daemon status            # строка службы: установлена / загружена / pid / последний выход (код или сигнал)
pult daemon uninstall         # снять службу; PULT_HOME не трогается
```

- **Что ставится.** `~/Library/LaunchAgents/dev.pult.daemon.plist` или `~/.config/systemd/user/pultd.service`,
  лаунчер `PULT_HOME/bin/pultd-launch` и файл `PULT_HOME/node-path`. Служба запускает только лаунчер: он сам
  находит node >= 22, если brew/nvm/volta его перенесли, и берёт точку входа из `PULT_HOME/current`, поэтому
  переключение версии не требует переписывать файл службы. Другое имя службы (второй `PULT_HOME`) —
  `PULT_SERVICE_NAME=<имя>`. Чужую службу (её файл указывает на другой `PULT_HOME`) CLI не перезаписывает,
  не снимает и не запускает.
- **Журналы.** Вывод процесса под службой — `PULT_HOME/logs/service.log` (строки лаунчера и падения до
  журнала демона; больше 5 МБ — лаунчер обрезает его при старте). Журнал самого демона — как раньше,
  `pult daemon logs` (`logs/pultd.log`, JSONL).
- **Код 78** — лаунчер не нашёл node >= 22 или точку входа (нет активной версии). `pult doctor` показывает
  это строкой «служба указывает на несуществующий node или точку входа».
- **Остановка.** `pult daemon stop` под службой — демон выходит с кодом 0, и служба его НЕ поднимает
  (`KeepAlive.SuccessfulExit=false` / `Restart=on-failure`); следующая команда поднимет его через менеджер
  служб (`launchctl kickstart`, а если служба не загружена — `launchctl bootstrap` / `systemctl --user start`),
  а не отсоединённым процессом. SIGTERM от
  `bootout`/`systemctl stop` — тоже выход с кодом 0. Демон ещё стартует (сокет молчит) — stop ждёт его
  сокет до 10 с и гасит штатно; сигнал — только если сокет так и не появился, и если менеджер после него
  поднимает демона снова, stop честно отвечает кодом 1.
- **Код 3 (lock держит другой демон) ведёт себя по-разному.** Под launchd это самовосстановление: служба
  перезапускает демона каждые 10 с и заберёт работу, когда чужой экземпляр уйдёт. Под systemd после пяти
  стартов за минуту (`StartLimitBurst`) служба останавливается совсем — это видно в `pult doctor`, лечится
  `systemctl --user reset-failed pultd.service && pult daemon install`.
- **Linux: linger.** Без него `systemd --user` гасит демона вместе с последней сессией. `install` включает его
  сам (`loginctl enable-linger`), а если не дали прав — печатает точную команду `sudo loginctl enable-linger <user>`
  и всё равно ставит службу. `uninstall` linger не трогает.
- **macOS: диалог доступа к ~/Desktop.** macOS спрашивает доступ к `~/Desktop`, `~/Documents`, `~/Downloads`
  у процесса — под службой это `node`. Если рабочая копия (`--dev`) или папка сессии агента лежит там, появится
  системный диалог «“node” would like to access files in your Desktop folder»: нажми «Разрешить», иначе демон под
  службой не прочитает свою точку входа или папку сессии. `install --dev` из такой папки предупреждает заранее.
  Руками проверить службу на своей машине — [`HUMAN-STEPS-F1-M4.md`](HUMAN-STEPS-F1-M4.md).
- **Приоритет службы: `ProcessType Standard`.** До 0.2.2 в plist стоял `Background` — фоновый приоритет launchd, который
  наследует всё, что запускает демон (`claude`, `codex`, `git`). Файл службы `pult update` не переписывает, поэтому после
  обновления с 0.2.1 и старше нужен `pult daemon install`; `pult doctor` (пункт «Файл службы») и `pult update` об этом напомнят.
- **Служба установлена, но не загружена** (её сняли `launchctl bootout` и не вернули): `pult daemon status` пишет
  «не загружена (загрузить: pult daemon install)», а любая команда, которой нужен демон, грузит её сама (`bootstrap`).
- **Демон поднят в обход службы.** Менеджер служб отказал — CLI поднимает демона напрямую и печатает
  «ВНИМАНИЕ: …» с тем, загружена ли служба, и командой возврата `pult daemon install`.

Замер 30.09.2026 на настоящем launchd (отдельная служба через `PULT_SERVICE_NAME`, временный `PULT_HOME`, node 26.10,
та же машина, что и рабочая служба). Старт — от `launchctl kickstart` до «демон слушает», между стартами больше `ThrottleInterval`:

| | plist `Background` | plist `Standard` |
|---|---|---|
| старт, 0.2.1 | 2,2–3,0 с (рабочая служба сразу после установки версии — 11 с) | 0,45–0,65 с |
| старт, 0.2.2 | 1,6–3,6 с | 0,37–0,41 с |
| `doctor.run`: демон молчит, 0.2.1 | 18,6–18,8 с (рабочая служба, по её журналу, — 44 и 94 с) | 1,0–1,9 с |
| `doctor.run`: демон молчит, 0.2.2 | 0,26–0,27 с | 0,002–0,08 с |
| `doctor.run` целиком, 0.2.1 → 0.2.2 | 21 с → 5,5–12 с | 2,2–3,2 с → 1,0–3,0 с (с проверкой сети) |

Один и тот же набор запусков (граф модулей демона, семь `--version`, логин-шелл, `claude auth status`,
`codex login status`) под launchd: `Background` — 22,8 с, `Standard` — 1,3 с, `Interactive` — 1,2 с. Отсюда два правила:
демон не запускает ни одного процесса до `listen` (кроме `ps` для lock) и не зовёт `spawnSync` на событийном цикле —
тест `test/daemon-responsive.test.ts` следит за обоими.

## Ф1 В4: обновление и install.sh

Версии живут в `PULT_HOME/versions/<v>` (каждая — отдельный `npm install --global --prefix`),
активная — симлинк `PULT_HOME/current -> versions/<v>`. Служба и `~/.local/bin/pult` смотрят через
`current`, поэтому переключение версии — это перестановка одного симлинка, а не переписывание файлов.

```sh
pult update --from pult-0.2.0.tgz   # поставить тарбол и переключиться (с пробой и автооткатом)
pult update --from pult-0.2.0.tgz --reinstall   # переставить НЕ активную версию, которая уже на диске
pult update --to 0.1.0              # переключиться на уже стоящую версию (ручной откат), тоже с пробой
pult update --list [--json]         # версии на диске: current, previous, bad
pult update                         # канал обновлений: latest.json из релизов GitHub (раздел M8c ниже)
pult update --check [--json]        # только проверить: 0 — последняя, 10 — есть обновление, 1 — не вышло
```

- **Как ставится.** Имя и версия берутся из `package/package.json` внутри тарбола; не `pult` — отказ.
  npm идёт `--offline`, с `HOME=PULT_HOME` и кэшем `PULT_HOME/npm-cache` (чужой `~/.npmrc` не читается,
  в настоящий `~/.npm` ничего не пишется), в `versions/<v>.partial`; после проверки (`bin/pultd`, точка
  входа демона, `pult --version` = v) каталог переименовывается в `versions/<v>`. Установка, убитая
  посреди npm, оставляет только `.partial` — версией он не считается и убирается следующим `update`.
  Два `pult update` разом не идут: второй отказывает по `run/update.lock`.
- **Проба.** После переключения `current` демон перезапускается: работал — `daemon.stop` (сессии
  остаются в реестре и возобновятся), служба стоит — `launchctl bootout` + `bootstrap` (не `kickstart -k`:
  его launchd после падения придерживает на 10–18 с) / `systemctl --user restart`, иначе отсоединённый
  спавн. `bootout` отвечает раньше, чем служба выгружена (замер: до 5,1 с, пока её процесс не вышел), и `bootstrap`
  в это время получает `5: Input/output error` — поэтому перезагрузка ждёт конца выгрузки (`launchctl print` до
  «службы нет», до 15 с). Менеджер служб всё же отказал — демон поднимается напрямую, а `pult update` в конце
  говорит, что служба осталась незагруженной, и чем её вернуть (`pult daemon install`); код выхода при этом 0. Демон НОВОЙ версии поднимается из `current`, а не из пакета обновляющего CLI (тот — старая
  версия). До трёх попыток: `hello_ok` за 10 с, `daemon.status` называет новую версию, и через 2 с демон
  всё ещё жив (ловит падение сразу после старта); процесс, вышедший до `hello_ok`, кончает пробу сразу —
  повтор детерминированного падения не лечит. Демона до обновления не было и службы нет — после удачной
  пробы он останавливается.
- **Откат.** Проба не прошла — `current` возвращается на прежнюю версию, лаунчер службы — из неё же,
  старый демон поднимается снова (если он был или его держит служба). Новая версия помечается `bad` в
  `update.json` и ОСТАЁТСЯ на диске для разбора; код 1, в тексте «откат на <previous>» и хвост вывода
  новой версии. Первой установке откатываться некуда: `current` снимается, код 1.
- **Хранение.** После удачного обновления остаются current, previous и ещё одна последняя по времени
  установки; `bad` удаляются первыми (запасное место достаётся исправной версии). current и previous не
  удаляются никогда; `versions/<v>-dev` от `pult daemon install --dev` — ссылки на рабочую копию, их
  уборка не трогает.
- **`pult doctor`** показывает, куда указывает `current` и какая там версия, и предупреждает «перезапусти
  демона», если работает демон другой версии.
- **Свой node (0.2.18, `src/update/runtime.ts`).** `runtime.env` в корне пакета пинит версию Node LTS и sha256
  тарболов nodejs.org под четыре платформы. `pult update` ДО остановки старого демона кладёт этот node в
  `PULT_HOME/runtime/node-v<версия>-<платформа>` (скачивание curl'ом с `--proto '=https'`, сумма до распаковки,
  распаковка в `.partial-<pid>`, `include/` и `share/` вырезаются — ~135 МБ вместо ~200) и пишет путь в
  `runtime/active`. Лаунчер службы, отсоединённый спавн и `pult ui` поднимают демона им, заглушка разрешений идёт
  на node демона; системный node — запасной путь, `node-path` остаётся его кэшем. Свой node главнее и явно
  переданного пути (`nodePath` у окна): окно держит путь неделями, а системный node сносит brew. Не скачалось — обновление не
  валится: предупреждение и `pult runtime install`. Откат возвращает указатель как был; после удачной пробы
  уборка оставляет node, нужные версиям на диске, и тот, на который смотрит указатель. Уже лежащий node не
  запускается для проверки: первый запуск свежего бинаря macOS проверяет до 30 с (замер), и по таймауту
  переставлялся бы каталог, на котором работает демон. Зачем всё это: 14.10.2026 `brew upgrade node` удалил node
  живого демона, macOS перестала пускать его детей в `~/Desktop`, и каждый ход claude там падал за секунду с
  «An unknown error occurred (Unexpected)». Официальный node зависит только от системных библиотек и подписан
  Node.js Foundation: после ПЕРВОГО разрешения на `~/Desktop` (macOS спросит один раз — это новый бинарь для неё)
  оно должно переживать смену его версий. **Переход с 0.2.17 и раньше:** `pult update` исполняет код СТАРОГО CLI,
  в котором своего node нет, — после обновления один раз `pult runtime install && pult daemon stop && pult daemon start`
  (или ставить тарбол новым CLI: `node <распакованный>/package/dist/cli/main.js update --from <tgz>`, как install.sh). `daemon.status.node` и пункт доктора
  `daemon.node` говорят, на каком node демон и не удалён ли он (сверка inode с бинарём при старте: установщик
  nodejs.org и apt кладут новую версию по тому же пути); `pult runtime [--json]` — то же для человека. Указатель
  на node чужой архитектуры (PULT_HOME перенесён с Intel-мака) не берётся: платформа сверяется по имени каталога.
  Прерванная проба помнит прежний указатель в `update.json` (`runtimeBefore`), откат перепроверки берёт его оттуда.
  В тестах сеть закрыта: под `PULT_TEST=1` тарбол берётся только из `PULT_TEST_NODE_TARBALL`. Окно (shell/) при
  отсутствии службы находит node по-старому (`PULT_NODE` → `node-path`), но спавн из пакета всё равно берёт свой.

**install.sh** (в корне репозитория; с M8c едет в каждом релизе GitHub) ставит Пульт с нуля. Он POSIX sh — прочитай до запуска:

```sh
sh install.sh --from pult-0.2.0.tgz                 # или --from https://…/pult-0.2.0.tgz
sh install.sh --from pult-0.2.0.tgz --no-service    # без службы: демон по требованию
sh install.sh --from … --home ~/.pult --bin-dir ~/.local/bin   # это значения по умолчанию
```

Ищет системный node >= 22 в PATH, распаковывает тарбол во временную папку и запускает из неё
`<node> package/dist/cli/main.js update --from <tgz>` — логика установки одна, в `pult update`. Затем
симлинк `<bin-dir>/pult -> PULT_HOME/bin/pult` (чужой файл на этом месте не трогает; каталога нет в PATH —
подсказка), `pult daemon install` (если нет `--no-service`) и `pult doctor --no-net`.

- **Без системного node (0.2.22).** Node нет или он старше 22 — установщик сам ставит свой node Пульта по пину
  `package/runtime.env` из тарбола, в той же раскладке, что `src/update/runtime.ts`: тарбол
  `https://nodejs.org/dist/v<версия>/node-v<версия>-<платформа>-<arch>.tar.gz` (или `PULT_NODE_MIRROR`, только https;
  curl `-q` с `--proto '=https' --tlsv1.2`), sha256 (`shasum -a 256` на macOS, `sha256sum` на Linux) сверяется с
  пином ДО распаковки, распаковка в `runtime/<имя>.partial-<pid>`, `include/` и `share/` вырезаются, на место — mv
  (соседняя установка успела раньше — своя копия выбрасывается, каталог с живым node не удаляется никогда). Пин
  разбирается так же строго, как `parsePin`. Архитектура на macOS — по железу (`sysctl hw.optional.arm64`), а не по
  `uname -m`: шелл под Rosetta иначе поставил бы x64. musl (Alpine) — подсказка поставить node из пакетов системы.
  Указатель `runtime/active` установщик НЕ пишет: этим node идёт `pult update`, и его `ensureRuntime` находит
  разложенный каталог и переставляет указатель, запомнив прежний для отката. Только если версия «уже стоит» (до своего
  node `pult update` тогда не доходит), а указателя нет или он мёртвый, — пишет его сам. Пакет без `runtime.env`
  (старше 0.2.18) или без лаунчера команды (0.2.18–0.2.21) и нет node — код 1 до установки и подсказка
  `brew install node`; итоговый `pult --version` обязан ответить, иначе код 1. В тестах (`PULT_TEST=1`) сеть не
  трогается: тарбол node — только `PULT_TEST_NODE_TARBALL`.
- **Лаунчер команды `service/pult` (0.2.22).** npm кладёт в `current/bin/pult` ссылку на `dist/cli/main.js` с
  `#!/usr/bin/env node` — она живёт на системном node. Лаунчер — POSIX sh: свой node по `runtime/active` (исполняемый и
  собран под эту машину — по имени каталога, без запуска, как `readActiveRuntime`; на Apple Silicon годен и darwin-x64
  через Rosetta), иначе системный >= 22 (PATH →
  `node-path` → известные места), и `exec` CLI активной версии (`current/lib/node_modules/pult/dist/cli/main.js`, для
  `--dev` — `current/dist/cli/main.js`). Нет node или активной версии — код 78 с подсказкой. `PULT_HOME` не задан —
  дом берётся по месту лаунчера (`<bin-dir>/pult` раскрывается на один уровень, каталог над `bin/`, если в нём есть
  `current` или `versions/`): после `install.sh --home DIR` экспортировать `PULT_HOME` не обязательно. `pult update` копирует его
  в `PULT_HOME/bin/pult` вместе с `pultd-launch` (и при «уже стоит», если файла нет); в пакете старше его нет —
  прежний остаётся, он от версии не зависит. CLI, поднятый своим node, не пишет его в `node-path` при `pult daemon
  install`: это кэш СИСТЕМНОГО node для лаунчера службы.
- **Совместимость.** Прежний симлинк `~/.local/bin/pult -> PULT_HOME/current/bin/pult` работает как раньше — на
  системном node; повторный `install.sh` переводит его на лаунчер. `pult update` из CLI старше 0.2.22 лаунчер команды
  не кладёт (его код не знает о нём) — его положит следующий `pult update` уже новым CLI или `install.sh`.

## Ф1 В4: worktree агента

Два агента в одной рабочей копии правят одни и те же файлы и делят один индекс. `--worktree` даёт агенту
свою рабочую копию того же репозитория (`git worktree`) на своей ветке — одной командой:

```sh
pult agent start w1 --kind claude --cwd ~/code/app/web --worktree feat/login            # ветки нет — от HEAD
pult agent start w2 --kind codex  --cwd ~/code/app --worktree fix/crash --base origin/main   # от указанной базы
pult agent list                  # … · worktree ~/.pult/worktrees/app-1a2b3c4d/feat-login (feat/login)
pult agent rm w1                 # агент удалён, worktree ОСТАЁТСЯ — печатается путь и команда уборки
pult agent rm w2 --worktree      # ещё и `git worktree remove` — только чистое дерево
```

- **Где папка.** `PULT_HOME/worktrees/<имя репо>-<8 hex sha256 пути репо>/<ветка, «/» → «-»>`. Вне репозитория —
  его `git status` не пачкается; хэш — два репозитория `app` в разных местах не делят папку. Если имя папки уже
  занято другой веткой (`a/b` и `a-b`), второй достаётся `…-<8 hex имени ветки>`.
- **Какая ветка.** Папка уже есть и в ней эта ветка — переиспользуется (агента можно удалить и завести заново).
  Ветка есть и нигде не выписана — выписывается. Ветки нет — заводится от `--base` или от HEAD `--cwd`
  (`--base` у существующей ветки ни на что не влияет — `agent start` об этом предупреждает). Ветка выписана
  где-то ещё (в самом репо или в другом worktree) — отказ с этим путём. Имя ветки судит `git check-ref-format`.
- **cwd агента** — папка worktree плюс тот же подкаталог, из которого звали: `--cwd ~/code/app/web` → `…/feat-login/web`.
  Подкаталога нет в выписанной ветке — отказ (worktree остаётся). `--cwd` не в git-репозитории — `invalid_params`.
- **Один worktree — один агент.** Второй агент в занятую папку не пускается: общий worktree — ровно то, от чего
  он спасает.
- **Реестр** помнит `worktree: {path, branch, repo}`; после рестарта демона агент возобновляется в той же папке.
  `agent list` показывает worktree в строке, `agent read` — строкой в stderr (stdout остаётся текстом модели).
- **Уборка.** `agent rm` папку не трогает. `agent rm --worktree` зовёт `git worktree remove` БЕЗ `--force`: правка
  или неотслеживаемый файл — отказ всей команды (код 1, текст git), агент остаётся. Агент посреди хода — тоже
  отказ: сначала `pult agent stop`. **Ветка не удаляется никогда** — в ней может быть неотправленная работа.
- **Git** зовёт демон с окружением по белому списку (инвариант 1: `GIT_DIR` из чужого хука не протечёт) и
  `GIT_TERMINAL_PROMPT=0`; `--force` не передаётся нигде. Пишет git в `PULT_HOME/worktrees` и в `.git` исходного
  репозитория (его служебные файлы worktree и новая ветка) — это разрешено инвариантом 8.

**Старт окна без доигрывания журнала (0.2.19, окно 0.1.8).** Раньше окно сворачивало весь журнал с нуля на
каждом старте: 18,6 МБ и 29 тыс. событий на 14.10.2026, +1,7 МБ в день (61 % — выводы инструментов). Теперь:
- `events.snapshot` — последние `daemon.started`, `background.changed`, `context.updated`, `usage.updated`,
  `limit.hit`, `net.blocked` по сессиям и время последней активности (без дельт и замеров контекста). Хранилище
  копит их в том же проходе, что строит индекс смещений, и на каждой записи. Статусы — из `agent.list`,
  разрешения — из `perm.list`; поток — с курсора снимка.
- `events.history {sessionId, before?}` — лента сессии, когда её открывают: файл `events/<сессия>.jsonl` → лёгкая
  история (`src/core/history.ts`): дельты одной реплики склеены (серия, закрытая итогом, — один символ), вывода
  инструментов нет (`elided`), вход до 300 знаков (`inputElided`); реплики и запросы разрешений целиком. Самая
  большая сессия — 4 МБ → 0,75 МБ. Отдаётся страницами до 512 КБ с конца, по началу хода: клиент рвёт соединение
  на строке больше 1 МиБ. «Показать раньше» в ленте — следующая страница (`before`). События сессии, пришедшие,
  пока история в пути, окно доигрывает поверх неё (`inflight`), а курсор истории становится «полом» ленты
  (`floors`): событие из очереди окна с номером не выше него второй раз не ляжет. Неотвеченные карточки старше
  последнего `daemon.started` гаснут. Снимок не трогает Inbox (`perm.list`) и статусы (`agent.list`). Сверено на
  24 настоящих сессиях: лента та же, страницы складываются в полную историю.
- `events.get {ids}` — полные события (до 200) для раскрытой строки инструмента; строки до 100 тыс. знаков,
  ответ — в бюджете страницы.
- Окно со старой оболочкой (белый список без этих методов) или старым демоном — прежнее доигрывание с нуля.

**О2 «внимание», часть 1 (0.2.21, окно 0.1.9)** — docs/14 «Непрочитанное и значок на доке», «Клавиатурная
разборка очереди», «Ошибки в Inbox и фильтры»:
- `src/sessions/attention.ts` — одна чистая классификация на демона, окно и оболочку. Событие внимания: `status.changed`
  idle с `turnId` или итог фонового хода (`reason: background_turn_done`) → `done`, `failed` → `failed` (кроме
  `reason: net_blocked`: причину уже несёт `net.blocked`), `limited` с `turnId` → `limit`,
  `permission.requested`/`question.asked` → `ask`, `limit.hit` → `limit` (кроме `allowed_warning`),
  `net.blocked`/`provider.blocked` → `blocked`. Причина — до 300 знаков одной строкой; `turnId` события — в
  поле `turnId` (по нему «Повторить»).
- Хранилище держит последнее событие внимания по сессии (`store.attention(name)`) — тем же проходом, что снимок, и
  на каждой записи; `session.ended {reason: rm}` и новая `message.user` его стирают (человек уже ответил).
  `agent.list` отдаёт его полем `attention`.
- Реестр: `lastSeenEventId` и `markedUnread`. Непрочитано: `markedUnread || attention.id > lastSeenEventId`
  (`isUnread`). Разовая миграция при старте (`seedSeen`): записи без отметки получают последний номер журнала —
  после обновления старые сессии не загораются все разом; отметка впереди журнала опускается до его конца. Новая
  сессия заводится с отметкой.
- `agent.seen {name, unread?, upTo?}` — отметка `max(прежняя, min(upTo, конец журнала))`, без `upTo` (CLI) — конец
  журнала; `unread` — `markedUnread`. Событий не пишет, без перемен не трогает диск. Окно шлёт `upTo` = номер
  события внимания на экране: пришедшее, пока запрос летел, остаётся непрочитанным.
- `agent.retry {name}` — реплика именно упавшего хода (`retryPrompt`): ошибка должна быть ошибкой хода (`turnId`);
  от события ошибки назад — ближайший `status.changed working` с тем же `turnId` (номера `t17` повторяются после
  рестарта демона), реплика — ближайшая `message.user` перед ним; граница — `session.ended rm`; новой реплики после
  ошибки быть не должно. Лимит аккаунта на простое, фоновый ход и страж вне хода — не повторяются. Занятая сессия
  (ход, отправка, удаление, ждёт человека) — отказ до всего; «видел» (до номера ошибки) ставится только после того,

## О3: ссылки `pult://` (0.2.26, окно 0.1.13)

Решение — docs/14 «О3 — ссылки `pult://`».

- **Разбор** — `shell/src/pultUrl.ts`, чистый: `checkPultUrl(url) → {ok, link} | {ok: false, reason}`,
  `parsePultUrl` — то же без причины. Виды: `pult://session/<имя>` → `{type: 'session', name}` (имя — по
  `SESSION_NAME_RE` демона, тест сверяет с `src/sessions/registry.ts`) и `pult://new?path&prompt&provider` →
  `{type: 'new', path?, prompt?, provider?}`. Ссылка снаружи — недоверенный ввод, отказ целиком: не `pult://<вид>`,
  `:` или `@` в сырой части до пути (логин, порт, пустой порт `session:`), `#`, сырые управляющие символы (`new URL`
  молча выбросил бы `\n` из `ses\nsion`), длиннее 128 КБ. Вид, путь и запрос берутся из сырой строки: URL сворачивает
  `session/../x` в `/x` и раскодирует `+` в пробел, а у нас `c++` остаётся `c++` (запрос — свой разбор с
  `decodeURIComponent`, битая процентная запись — отказ). `path` — абсолютный, без сегментов `..`, без `\p{Cc}`,
  `\p{Cf}` (U+202E, U+200B, U+FEFF…), U+2028/U+2029, до 4096; `prompt` — то же, кроме `\n` и `\t`, до 10 000
  кодовых точек и 200 строк; `provider` — `claude` или `codex`; известный параметр дважды — отказ; неизвестные —
  пропуск. Отказ — строка в лог оболочки с причиной и длиной, без самой ссылки (в реплике может быть личное).
- **Папка из ссылки — только знакомая.** Сессия в чужой папке исполняет её хуки и настройки проекта, поэтому на
  выходе из ворот main сверяет `path` с `project.list` и папками сессий из `agent.list` (`matchKnownPath`:
  `realpath` с обеих сторон, равенство, а не префикс; демона ждёт до 15 с). Совпало — в диалог идёт путь, как его
  хранит демон; нет (или демон не ответил) — `path` выброшен, `pathRejected: true`, диалог пишет «папка из ссылки
  не из твоих проектов — выбери сам», папку выбирают кнопкой «Выбрать…».
- **Оболочка** (`main.ts`): `open-url` (macOS) вешается до `ready` — ссылка холодного старта приходит раньше окна;
  ссылка из argv — у первого экземпляра (`linkFromArgv(process.argv)`) и у второго (`second-instance`, Linux;
  отвергнутая ссылка поднимает окно, как второй запуск без ссылки). Предел частоты `LinkRate`: годная ссылка раньше
  1,5 с после предыдущей отброшена (в PULT_TEST окно задаёт `PULT_TEST_LINK_GAP_MS`). Дальше `LinkGate`: до конца
  `boot()` держится последняя ссылка (вытесненная или потерянная при провале старта — строка в лог), потом сверка
  папки и `openAt(target)` — тот же путь, что у уведомления и строки меню; кадр помечен `link: true`. Окно —
  `app.focus()` без `steal` (кроме PULT_TEST): чужая ссылка не выхватывает клавиатуру, значок в доке подпрыгивает.
- **Регистрация схемы:** `build.protocols` в `shell/package.json` → `CFBundleURLTypes` в Info.plist (check-app
  сверяет); `app.setAsDefaultProtocolClient('pult')` — только `app.isPackaged && !PULT_TEST`: `npm start` из
  рабочей копии и e2e не перехватывают схему у установленного Pult.app (e2e проверяет флаг
  `__pultTestProtocolClient === false`). `check-app.mjs --launch` запускает собранную копию из `shell/out/`:
  LaunchServices может её запомнить как ещё одного владельца схемы — обработчиком по умолчанию она от этого не
  становится, но после проверки стоит удалить `shell/out/` или поставить свежий Pult.app.
- **Мост** без смены версии: кадр `navigate` — `NavTarget` = `NotifyTarget` + `newSession?: NewSessionPrefill` +
  `link?: true`. Старая оболочка их не шлёт, старый интерфейс их не читает.
- **Окно.** `ui/src/model/newAgent.ts`: `linkPrefill` (вторая проверка кадра теми же правилами), `linkForm`
  (провайдер, папка и имя из неё, первая реплика; модель, усилие, ветка — по умолчанию), `promptStats`. Диалог из
  ссылки: пометка «заполнено по ссылке», папка целиком с переносом (без `shortPath`), поле реплики растёт по тексту
  (до 360 px, дальше прокрутка) и счётчик «N строк · M знаков», «Завести» заперта первую секунду. Открытый «Новая
  сессия» ссылка не подменяет — строка в шапке «закрой диалог и открой ссылку снова». `ui/src/lib/linkGuard.ts`:
  после перехода по ссылке фокус снимается, окно 500 мс глотает клавиши (кроме модификаторов и Escape; слушатель на
  `window` в фазе захвата), поле ввода сессии из ссылки фокус не берёт (`takeAutoFocus`). `agent.start` шлёт только
  «Завести». Ссылка на сессию, которой нет (после первого `agent.list`), — строка в шапке.
- Тесты: `shell/test/unit/pultUrl.test.ts` (годные, кривые и злые ссылки, `+`, невидимые символы, 200 строк,
  `matchKnownPath`, `LinkRate`, ворота), `checkApp.test.ts` (`build.protocols`, проверка `CFBundleURLTypes` в
  check-app), `ui/test/model.test.ts` (`linkPrefill`, `linkForm`, `promptStats`, `linkGuard`), e2e
  `shell/test/e2e/links.test.ts`: холодный старт ссылкой в argv (`launch({args, env})`), чужая папка → выбор
  руками, папка проекта через симлинк, запертая «Завести», диалог не подменяется, глотание клавиш и фокус,
  предел частоты, злые ссылки, закрытое окно.

## M8c: канал обновлений (0.2.27, окно 0.1.14)

Веха M8c плана «Пульт до 1.0». Источник обновлений — релизы GitHub, а не VPS из черновика Ф7 (docs/08 §4–5): своего
сервера нет, и держать его ради одного файла незачем. Код — `src/update/{manifest,keys,fetch,channel,checker}.ts`,
сравнение версий вынесено в `src/core/semver.ts` (его берёт и окно).

**Файлы релиза** (`pawellazarew/pult`): `pult-<v>.tgz`; `pult.tgz` — те же байты под постоянным именем для
install.sh; `install.sh`; `Pult-<appv>-arm64.zip` (`ditto -c -k --keepParent`); `Pult-arm64.zip` — те же байты под
постоянным именем для README (`…/releases/latest/download/Pult-arm64.zip`: версию окна 0.1.x новичок не угадает; в
манифесте — имя с версией); `latest.json`. Адрес по умолчанию —
`https://github.com/pawellazarew/pult/releases/latest/download/latest.json` (GitHub сам ведёт `latest` на свежий
не-черновик и не-пререлиз); перебивается `updates.url` в `config.json` и `PULT_UPDATE_URL` — оба только https.
Последний релиз с нуля: `curl -q --proto '=https' -fsSLO …/latest/download/install.sh && sh install.sh --from
https://github.com/pawellazarew/pult/releases/latest/download/pult.tgz` — `--from` с https-адресом install.sh умел и
раньше (curl `--proto '=https'` действует и на редиректы).

**latest.json — подписанный конверт одним файлом**:

```json
{"schema":1,"keyId":"<hex8>","payload":"<base64 байтов манифеста>","signature":"<base64 Ed25519 над этими байтами>"}
```

Манифест внутри: `{"schema":1,"version":"1.0.1","released":"<ISO>","notes":"<https страницы релиза>",
"package":{"url","sha256","size"},"app":{"version","minVersion","darwin-arm64":{"url","sha256","size"}}}`.
Отдельного `.sig` нет: два скачивания — гонка (релиз перевыложили между ними) и два места подмены. Подпись — над
СЫРЫМИ байтами payload: канонизации JSON нет, и тот же объект с другим порядком ключей дал бы другую подпись.
Порядок проверки (`verifyEnvelope`): размер ≤ 64 КБ → разбор конверта → `schema` конверта = 1 → ключ по `keyId` из
доверенных → подпись → и только потом `JSON.parse` манифеста; разборщик не видит неподписанных байтов. Незнакомая
`schema` конверта или манифеста — отказ с подсказкой поставить новый Пульт руками (`--from`); незнакомые поля внутри
той же схемы пропускаются. Всё через `node:crypto` (Ed25519), зависимостей не прибавилось.

**Правила (не ослабляются ни для кого; тест подставляет функцию запроса, а не http):**
- https — для адреса latest.json, для адресов из манифеста и для КАЖДОГО редиректа, до запроса к нему; логин в
  адресе — отказ; не больше 5 редиректов. GitHub отдаёт файлы релиза 302-м на `objects.githubusercontent.com` — https,
  проходит;
- потолки по ПРОЧИТАННЫМ байтам, а не по Content-Length: latest.json ≤ 64 КБ, тарбол ≤ 200 МБ (в манифесте) и не
  больше `package.size` (обрыв посреди загрузки); таймауты: latest.json 30 с, тарбол 15 мин всего и 60 с без байта;
- тарбол: размер и sha256 = манифест, иначе файла нет и ничего не ставится; версия внутри тарбола = `version`
  манифеста (`installTarball(… expectVersion)`);
- только вперёд. **Решение по пререлизам:** каналом они не ходят вовсе — `version`, `app.version`, `app.minVersion`
  строго `x.y.z`, иначе манифест отвергается (и `release.mjs` такой не соберёт). Пререлиз владелец ставит `--from`.
  Ставится только `version` строго новее активной (`compareVersions`: `1.0.1 > 1.0.1-dev > 1.0.0`); та же или старше —
  «уже последняя» / «новее канала», код 0;
- версия, помеченная `bad` (не прошла пробу на этой машине), сама не ставится — иначе «Обновить» крутило бы
  установку и откат по кругу; повтор — `pult update --to <v>` руками;
- активная версия — рабочая копия (`daemon install --dev`) — канал её не трогает, отказ с подсказкой.

**Почему fetch Node, а не curl.** Редиректы руками (`redirect: 'manual'`): каждый адрес проверяется на https до
запроса — у curl то же обещает `--proto-redir`, но проверить это в тесте можно только фальшивым curl; потолок — по
прочитанным байтам; демон не спавнит процесс раз в сутки; тест подставляет `HttpGet` и не ослабляет правил. Цена:
fetch Node 22–24 не читает `HTTPS_PROXY`. Демон под launchd прокси-переменных и не видит (у владельца прокси — в
функции zsh, см. config.ts), а GitHub доступен напрямую; понадобится прокси — `updates.proxy` отдельной задачей.

**Ключи и ротация.** Доверенные ключи — `src/update/keys.ts`: `{id, publicKey}`, `publicKey` — сырой ключ base64
(32 байта) или SPKI (PEM / base64 DER), `id` = первые 8 hex sha256 сырого ключа; `id` сверяется с ключом на каждой
проверке — опечатка в файле даёт «ключ испорчен», а не доверие. **Список выходит ПУСТЫМ**: ключ владелец заводит после
ревью — `node scripts/release-keygen.mjs` (закрытый PKCS8 PEM в `~/.config/pult-release/ed25519.pem`, каталог 0700,
файл 0600, перезаписи нет; на экран — только открытый ключ, keyId и готовая строка для keys.ts), строку — в keys.ts
отдельным коммитом, PEM — в менеджер паролей. До этого `pult update` и `--check` отвечают «в этой сборке нет ключа
релизов», `--from` работает как раньше. Ротация: новый ключ дописывается в keys.ts и выходит релизом, подписанным
СТАРЫМ; следующий релиз подписывается новым; старый убирается, когда версий без нового ключа не осталось. Утёкший
ключ — убрать сразу (тем же порядком), но см. угрозу 5: ротация не спасает от того, кто уже держит ключ.

**CLI.** Голый `pult update` (`updateLatest`) — целиком под `run/update.lock`: latest.json → проверка → тарбол в
`PULT_HOME/downloads/pult-<v>.tgz.partial-<pid>` → rename → `installTarball` (тот же путь, что `--from`: `.partial`,
проба, автооткат; в `update.json` попытка записана как `action: "channel"`) → тарбол удаляется; следы прерванных
запусков в `downloads/` убирает следующий запуск под тем же lock. `pult update --check [--json]` ничего не ставит;
код 0 — ставить нечего (последняя, новее канала, bad, рабочая копия), **10 — есть что ставить** (не 2–5: те заняты
ошибками CLI, скрипт отличит «есть обновление» от сбоя), 1 — проверить не вышло. JSON: `current`, `latest`
(`version`, `released`, `notes`, `app`), `newer`, `bad`, `available`, `dev`, `url`, `window: {installed, minVersion,
outdated}` — версия окна читается из `Info.plist` Pult.app в тех же местах, что у `pult ui` (под PULT_TEST — только
`PULT_TEST_APP_DIRS`).

**Демон** (`checker.ts`). Первая проверка — через 60 с после старта, дальше раз в сутки ± час (с 0.3.3 — раз в 6 ч
± 30 мин и по фокусу окна, раздел «Обновление из окна»). Сутки — по СТЕННЫМ
часам с пересчётом раз в 10 мин, а не одним `setTimeout` на 24 ч: монотонные часы на macOS стоят, пока ноутбук спит.
`updates.check: false` — ни одного запроса сам и старый итог не показывается; ручной `update.check` (его просит
человек) работает. Итог — в памяти и в `PULT_HOME/update-check.json` (после рестарта окно сразу видит «Доступна …»);
сбой сети пишет `error`, но прежний `latest` не прячет. RPC: `update.status`, `update.check` (проверить сейчас; вторая
во время первой ждёт её), `update.apply {force?}`; тот же объект — `daemon.status.update`. **PROTOCOL_VERSION остался
1:** методы и поле только добавлены, а рукопожатие сверяет версию строгим равенством — смена отрезала бы старые окна и
CLI ради полей, которые они и так пропускают.

`update.apply`: ходы идут (`working`, `blocked_permission`, `blocked_question` — рестарт демона оборвал бы их) и нет
`force` → `{waiting: N}`, обновление начнётся само, когда кончится последний. Пересчёт — на каждом событии журнала, но
на СЛЕДУЮЩЕМ обороте цикла (`setImmediate`): менеджер сессий обновляет статус хода ПОСЛЕ рассылки события, и пересчёт
сразу видел бы конец хода ещё `working` (поймано тестом); страховка — пересчёт раз в 5 с. `force: true` — сразу.
Запуск — ОТСОЕДИНЁННЫЙ `pult update` через лаунчер команды `PULT_HOME/bin/pult` (нет его — node демона + свой
`dist/cli/main.js`), вывод — в `logs/update.log`, окружение — как у демона по требованию плюс то, что нужно службе.
На Linux под службой — `systemd-run --user --scope --collect`: systemd при рестарте службы гасит всю её контрольную
группу (`KillMode=control-group`), setsid не спасает; ребёнку передаются `XDG_RUNTIME_DIR` и
`DBUS_SESSION_BUS_ADDRESS` — без них и `systemd-run --user`, и `systemctl --user restart` падают с «Failed to connect to
bus». launchd гасит группу процессов задачи, а отсоединённый ребёнок — в своей сессии; обёртка не нужна (проверено на
настоящем launchd при ревью M8c: setsid-ребёнок переживает `launchctl bootout` задачи-родителя).
Ребёнок вышел не с 0 (подпись, загрузка, проба с откатом) — `apply.state = failed` с путём к журналу. Удачный
`pult update` останавливает демона сам; окно переподключается, как после любого рестарта (`DaemonLink`, e2e
`bridge.test.ts` «демон убит … поднят»), и e2e `update.test.ts` гоняет «Обновить» до настоящего ребёнка.
Ожидание живёт в памяти: рестарт демона его снимает (человек нажмёт ещё раз). Фоновые субагенты (процесс Claude
после конца хода) ходом не считаются — «Обновить» их не ждёт.

**Поправки ревью M8c** (тот же 0.2.27):
- **Пока ставится, ходы не заводятся.** `pult update` секунды-минуты качает и ставит, прежде чем перезапустить демона;
  ход, начатый в это время, оборвался бы. Менеджер сессий получает `holdTurns()`: пока `apply.state = applying`,
  `prompt` и `say` (реплика, «прервать и сказать», «Повторить», очередь) отвечают кодом `updating` и «Пульт обновляется —
  отправь после перезапуска», очередь реплик стоит. Окно не стирает поле ввода при отказе — черновик остаётся (e2e).
- **Одно «Обновить» за раз:** второй вызов во время первого (там await проверки) получает тот же промис; после await
  состояние перепроверяется; выход и ошибка ребёнка учитываются, только если это ТЕКУЩИЙ ребёнок — запоздалый выход
  прежнего не затирает «ставится» нового.
- **`--expect <версия>`:** демон запускает `pult update --expect X`; в канале уже другая версия — отказ, а не тихая
  установка того, чего человек не видел. С 0.3.5 `--expect` ещё и не проверяет идущие ходы: их уже дождался демон (или
  человек нажал «Сейчас»); `pult update` руками — проверяет (раздел «Разрешения…» ниже).

  update.log», крестик прячет до следующей неудачи.

- **Повторы неудачной проверки:** 15 мин → 1 ч → 6 ч, дальше снова сутки; удача сбрасывает счёт.
- **Ошибки канала не в плашке.** Нет сети, в канале нет релиза (GitHub отвечает 404) или адрес не тот — это не
  поломка. Ошибка проверки видна в `pult update --check` (код 1) и пунктом `pult doctor` «Канал обновлений» (warn, не

  updates.url; поставить вручную: pult update --from <тарбол>» (до M8b подсказка говорила о приватном репозитории).

**Выпуск релиза** (владелец, локально; закрытый ключ в CI не едет никогда). `node scripts/release.mjs <x.y.z>` —
`.mjs`, а не `.sh`: подписывать всё равно node, а проверять релиз надо кодом из СОБРАННОГО тарбола. Шаги: чистое
дерево на main и версия в package.json = аргумент → `PULT_E2E=1 ./scripts/ci-check.sh` → `npm pack` (+ копия
`pult.tgz`, + install.sh) → Pult.app (`cd shell && npm ci && node node_modules/electron/install.js && npm run
dist:mac`) → zip (+ копия `Pult-arm64.zip`) → манифест (`app.minVersion` — `WINDOW_MIN_VERSION` из тарбола) → подпись ключом из
`--key` / `PULT_RELEASE_KEY` / `~/.config/pult-release/ed25519.pem` (ключ доступен не только владельцу — отказ) →
самопроверка `verifyEnvelope` из `dist/` тарбола его же `keys.ts` (ключ подписи не из них — отказ: такой latest.json
отвергнет каждый Пульт) и сверка sha256 файлов → `release/<v>/`. По умолчанию СУХОЙ прогон: печатает
`gh release create v<v> … --draft <файлы>` и `gh release edit v<v> --draft=false --latest`; `--publish` выполняет их.
Черновик — чтобы `releases/latest` не указывал на релиз, у которого ещё нет тарбола. Флаги репетиции: `--out`,
`--no-app`, `--app-zip <zip>` (готовый zip окна вместо сборки), `--skip-checks` и `--trust <открытый ключ>` (три
последних с `--publish` — отказ). `Pult-arm64.zip` в v0.3.1 доложен руками (`gh release upload`) — релиз вышел до
этого шага. `release/` — в .gitignore.

**Модель угроз** — что закрывает каждая мера и чего НЕ закрывает:
- **Украден токен GitHub / взломан аккаунт.** Злоумышленник выкладывает любой релиз. Подпись: без закрытого ключа
  latest.json не пройдёт, а тарбол сверяется по sha256 из подписанного манифеста. НЕ закрыто: удаление релизов и
  отдача старого подписанного latest.json (угроза 3), подмена `install.sh` и `pult.tgz` для НОВЫХ установок —
  install.sh не подписан, первая установка доверяет GitHub и TLS.
- **MITM.** https на каждом шаге и каждом редиректе (TLS Node), поверх — подпись и sha256: подменённый ответ не
  пройдёт, даже если TLS обманут. НЕ закрыто: блокировка (обновлений просто нет) и то, что видно, что Пульт ходит к GitHub.
- **Повтор старого манифеста.** Старый latest.json подписан честно и проверку подписи проходит, но ставится только
  версия строго новее активной — откатить человека назад нельзя. НЕ закрыто: заморозка — старый манифест можно отдавать
  вечно, и человек не узнает о новой версии (срока годности у манифеста нет; `released` на свежесть не проверяется).
- **Испорченная загрузка.** Размер и sha256 из подписанного манифеста, потолки, недокачанный файл удаляется, версия
  тарбола = версии манифеста; дальше обычная проба и автооткат. НЕ закрыто: честно подписанный, но сломанный релиз —
  его ловит только проба (откат и `bad`), а не подпись.
- **Взломана машина релиза.** Ключ лежит у владельца PEM-ом без пароля: кто владеет машиной, подпишет что угодно, и
  каждый Пульт это поставит. Закрыто частично: ключ только локально (не в CI, не в репо), 0600, копия в менеджере
  паролей; после утечки — ротация, но злоумышленник с ключом может выпустить релиз со своим keys.ts раньше. НЕ закрыто:
  пароль на ключе, аппаратный ключ, второй подписант (порог) — после 1.0.

## M9: публичное дерево (0.3.0)

Публичный репозиторий — НОВЫЙ, с одним коммитом «Pult 0.3.0» и без истории дизайна (решение владельца 20.10.2026).
Дерево для него собирает скрипт, а не ручное копирование:

```sh
node scripts/public-tree.mjs /tmp/pult-public     # папки быть не должно (или пустая), и она вне репозитория
cd /tmp/pult-public && npm ci && PULT_E2E=1 ./scripts/ci-check.sh
```

Что делает `scripts/public-tree.mjs`: берёт `git ls-files` рабочего дерева, выбрасывает пути из
`scripts/public-exclude.txt` (глобы в стиле gitignore, у каждого — комментарий «почему»), копирует остальное с битами
исполнения, делает `git init` и ОДИН коммит от автора, записанного в скрипте (`AUTHOR`). Ничего не пушит. Потом три
проверки, любая находка — код 1 (дерево остаётся на диске для разбора):

- **ссылки** — ни один оставшийся файл не указывает на выброшенный: ссылки Markdown, пути в обратных кавычках,
  `import`/`require`, пути фикстур, файлы, которые читают скрипты. Путь разрешается от корня и от папки файла,
  `<плейсхолдер>` и `*` — шаблон, `{a,b}` раскрывается. Исключение одно: нога спайка (`spike/<нога>/…`) может называть
  свой выход — `logs/` и `results.json`, которые `.gitignore` теперь игнорирует; список — `PUBLIC_TREE_VERBOSE=1`;
- **страж утечек** — `scripts/ci-leakguard.mjs` по всем файлам выгрузки;
- **шаблоны** — то, чего страж утечек не знает: домашние пути (кроме `you`/`user`), личная почта, адрес прокси
  владельца времён спайка, `loc=`/`colo=` со значением (страна и датацентр выхода), имена рабочей организации,
  её домена и других проектов владельца, ссылки на артефакты claude.ai; список — `PATTERNS` в скрипте. Каждое
  попадание печатается; проходят только записанные в `ALLOW` с причиной (адрес прокси — в docs, README и обвязке
  спайка; почта — только строка `AUTHOR` скрипта). Страна выхода в примерах и фейках — заглушка `XX`.

Что выброшено и почему (точные глобы и причины — в самом `public-exclude.txt`; здесь словами, потому что путь
к выброшенному файлу в оставшемся — сама находка проверки): сырые журналы прогонов всех ног спайка (папки `logs`
ног) и их таблицы вердиктов, сводка результатов спайка, записи воркфлоу проверяющих, захваченные выводы проб
`spike/env` (в том числе слепок окружения логин-шелла владельца), ресёрч с вердиктами проверяющих, страницы
дизайна v0.5 и v0.6 и скрипт рендера их картинок.
В самом публичном репозитории выбрасывать уже нечего: глобы ничего не находят («exclude pattern matched nothing»), а
проверка ссылок не спрашивает `git check-ignore` о пустом списке (на пустой строке он падал с «empty string is not a
valid pathspec»; код 1 у него значит «ничего не игнорируется», а не ошибку).
Скрипты спайка, слепки схем Codex/opencode, фикстуры, тесты и нумерованные документы остаются.

Исходный репозиторий согласован сам с собой: оставшиеся файлы не ссылаются на выброшенные (DELTA и DEV пишут
«журналы прогонов в публичное дерево не входят» вместо путей), выход прогонов спайка в `.gitignore`, клиенты ног Codex
и opencode сами создают `logs/`. Разработка после M9 идёт в публичном репозитории; повторный прогон скрипта —
проверка, что новое не потянуло ссылку на выброшенное.

    новому демону и зовёт `settings.get`/`providers.check`): стало — `done`; нет — откат и bad (проба честно не прошла);
  * новое встало, а окно ещё не открывали (swap/swapped) — обрыв наш: откат БЕЗ bad, повторить можно;
  * оборван откат — довести, bad.
  Окно было открыто — открыть. Восстановление не прошло — журнал остаётся, «Обновить окно» отказывает «прошлое
  обновление окна не доведено» до перезапуска демона. Потом уборка `apps/staging-*`, `apps/failed-*` и СВОИХ
  `.Pult.app.{incoming,failed,old}-*-<метка>` рядом с окном (кроме прежнего окна, ждущего первого запуска).
- **Остановка демона:** сначала отказы ожидающим разрешениям и адаптеры (инвариант 5), потом обновление окна — не
  дольше 3 с (launchd добивает службу SIGKILL через 5 с). До закрытия окна работа бросается («демон останавливается»,
  ничего не тронуто); посреди пробы — проба просыпается и выходит, окно не гасится, журнал (фаза health) — старту.
  Отдельно (было и до 0.3.4, задача на потом): остановка адаптера codex может идти до 6 с, и с ней остановка службы
  может не уложиться в 5 с launchd до SIGKILL.
  Ошибки подготовки и уборки (EPERM, ENOTEMPTY) пишутся в итог и журнал демона, необработанных отказов нет.
- **Черновики.** Окно кладёт непустой черновик поля в localStorage (`pult.drafts`: по сессии, неделя, до 50, до
  100 000 символов) через 0,5 с тишины набора, на `pagehide`/`beforeunload` и при смене сессии; новое окно ставит его в
  поле той же сессии; поле опустело — запись убирается.

**Модель угроз (дополнение к M8c):**
- **Доверие то же, что у пакета:** подпись latest.json ключом релизов и sha256/размер zip из него. Подменённый zip,
  чужой канал без ключа и MITM не проходят. НЕ закрыто: всё, что не закрыто у пакета (украденный ключ — см. M8c).

  проверяет при первом запуске. Подпись манифеста — единственный рубеж доверия; это осознанно (то же, что у тарбола
  пакета, исполняемого node без всякого Gatekeeper).

## Разрешения: что видно и что разрешает ⌘Enter (0.3.5, окно 0.1.15 без замены)

Ревью пути разрешений (PR #13, внешний вклад) и доводка после него. Общий принцип: человек разрешает только то, что
видел, и только там, где смотрит.

- **Показано не всё (`concealed`).** Брокер редактирует вход до публикации (инвариант 7), а решение возвращает
  ИСХОДНЫЙ вход: `ssh root@prod.example.com` в карточке — `ssh <email>`. Поэтому `concealed: true` в
  `permission.requested` и `perm.list`, если редакция что-то заменила (`JSON.stringify` до и после) или адаптер сам
  подрезал вход (Codex: `redact` + строки до 2000 знаков, массивы до 40 элементов с хвостом `…(ещё N)`); поле есть и в
  типе запроса адаптера (`AdapterDeps.askPermission`, src/adapters/types.ts). Карточка — строка «Показано не всё …»
  словами своего вида (`concealedNote`, ui/src/model/permissions.ts): команда — «Исполнится исходная команда», правка и
  прочее — «исходный ввод», вопрос (AskUserQuestion, requestUserInput) — «Модель видит вопрос целиком … пропусти», без
  «команды». `pult perm list` — `ВНИМАНИЕ: показано не всё`. Журнал по-прежнему отредактирован.
- **⌘Enter разрешает только видимую карточку** (`focusedRequest`, ui/src/model/inbox.ts). Видимы: запрос текущей
  сессии — когда её лента уже загрузилась (`ownShown`: пока `hydration` не `done`, карточки на экране нет), и карточки
  открытого Inbox с учётом фильтра. Закрытый Inbox чужих не показывает — до #13 откат шёл на самый старый запрос любой
  сессии. Выбор человека (клик по карточке) держится, пока карточка видима.
- **⌘Enter в поле реплики — только своя сессия** (`composerApproves`). Человек печатает сессии A, и карточка сессии B,
  пусть выделенная в открытом Inbox, этой клавишей не разрешается: `permFocused` поля — «выделен запрос ЭТОЙ сессии»
  (поле с ходом и текстом прерывает и говорит, а не отдаёт клавишу окну), и обработчик окна, получив ⌘Enter из поля
  (`data-testid="composer"`), тоже берёт только запрос текущей сессии. Вне поля — правило выше. Вопрос модели ⌘Enter
  не отвечает нигде.
- **Папка сессии — не над `PULT_HOME`** (`coversPultHome` → `coversDir`, src/core/paths.ts: realpath обоих, сравнение по
  частям пути; `PULT_HOME` под папкой `..x` — накрыт ею, сосед `..x` — нет). `agent.start` отказывает, если папка сессии
  — `PULT_HOME` или его предок: в `workspace` (Claude `acceptEdits`) и `ask` (Codex `workspace-write`) агент переписал бы
  `config.json` (а `notifyCommand` демон исполняет через `/bin/sh -c` вне песочницы). Проверяется НАСТОЯЩАЯ папка
  сессии: без worktree — `--cwd` до всего прочего; с worktree — папка worktree (`PULT_HOME/worktrees/…`), так что
  репозиторий в `~` с `--worktree` не ложный отказ. Сессия из `sessions.json` с такой папкой (заведена до проверки):
  ход (`prompt`, значит и очередь, «Повторить», «прервать и сказать») и `agent.configure` на любой режим шире «Только
  чтение» — `invalid_params` с подсказкой `pult agent set <имя> --approval read-only`; «Только чтение» — можно.
- **Папка — дом или выше — предупреждение, не отказ** (`HOME_CWD_WARNING`, src/sessions/settings.ts). PULT_HOME может
  лежать вне дома, и тогда `~` проходит проверку выше, но агент получает `~/.claude`, `~/.codex`, `~/.zshrc`. В «+ Сессия»
  — красная строка под папкой (`homeWarning`: окно угадывает дом по форме пути, как `shortPath`; без worktree, режим не
  «Только чтение»), `pult agent start` — строка `внимание — …` в stderr (realpath, `os.homedir()`).
- **Умер `claude` — его вопрос снимается** (инвариант 5). Заглушка `pult mcp-ask` держит соединение с демоном, пока ждёт
  ответа; закрылось оно (процесс убит вместе со своим `claude`) — `Connection.closed` (AbortController) срабатывает, и
  брокер (`request(req, {signal})`) отказывает с `pult: процесс агента завершился`, `by: provider_gone` — как
  `cancelPermissions` у Codex. Ответ, пришедший раньше, не трогается; умер ещё до вопроса — отказ сразу за
  `permission.requested`. Права `perm.request`/`perm.resolve` и токен этим не менялись.
- **`required` без прокси — закрыто.** `network.<провайдер>.mode = "required"` без `proxy` больше не становится `off`:
  `validateConfig` оставляет режим и предупреждает, `checkNetwork` без проб отдаёт `path: none`, `reason: no_proxy`, ход
  отказан (`blocked_network`, `net.blocked`) строкой `netRefusal` — «mode = "required", а proxy не задан; укажи proxy или
  mode "off"»; `pult doctor` — fail с той же подсказкой, окно — «режим required, а прокси не задан». `auto` без прокси —
  по-прежнему `off`.
- **`pult update` из CLI не обрывает ходы.** Канал, `--from`, `--to` перезапускают демона; окно в этом случае ждёт конца
  ходов (checker.ts), а CLI ждать в фоне некому — он отказывает: `pult update: идут ходы: N — … дождись или --force`
  (код 1, демон не тронут). Счёт тот же, что у checker, — `daemon.status.turns` (`working`, `blocked_permission`,
  `blocked_question` и заводящиеся ходы); нет демона или старый демон без поля — проверки нет. `--force` — не ждать
  (раньше флаг был только у `--app`; с `--list`/`--check` — отказ). `--expect` (так зовёт сам демон) не проверяет.
- Тесты: `test/perm.test.ts` (тип `concealed`, `signal` брокера, настоящая заглушка убита посреди вопроса → отказ в
  журнале), `test/sessions.test.ts` (настоящий `..x`, сессия из sessions.json: ход и `configure` — отказ, «Только
  чтение» — ход идёт), `test/worktree.test.ts` (репозиторий над PULT_HOME: без worktree — отказ, с worktree — папка в

## Страж сети: правило в «Настройках» (0.3.6, окно 0.1.15 без замены)

Просьба владельца: выбирать страны, откуда работать можно или нельзя, из окна. Оболочка не менялась: окно ходит
через `settings.get|set` и `doctor.run`, которые уже в белом списке 0.1.15.

- **Правило** — `network.guard: {mode: 'deny' | 'allow', countries: string[]}` в config.json, одно на claude, codex и
  opencode (свои правила у провайдеров — позже, не сейчас). Чистые функции — `src/core/guard.ts` (их берут демон, CLI и
  окно): коды ISO 3166-1 alpha-2 заглавными, вшитый список (249 + `XK`: так Cloudflare в `loc=` называет Косово).
  `deny` — отказ, если страна выхода в списке (как было всегда); `allow` — отказ, если её в списке НЕТ (причина
  `not_allowed_country`); неизвестная страна — отказ в обоих режимах (`unknown_location`). По умолчанию — прежний
  запретительный список `RU, BY, CN, IR, KP, SY, CU`.
- **Перенос.** Прежний верхний `guardCountries` читается как `{mode: 'deny', countries}`. Есть оба — действует
  `network.guard`, предупреждение в журнал на старте («guardCountries не читается»). `writeConfig` пишет страж только в
  `network.guard`. Мягкий разбор файла: регистр режима и кодов прощается, чужие коды отбрасываются с предупреждением;
  всё, что правилом не разобрать (не объект, режим не deny|allow, `countries` не список), — ЗАКРЫТО (`closedGuard`:
  allow без стран), а не откат на `guardCountries` или умолчание: тихий откат пустил бы ходы оттуда, откуда человек их не
  ждёт. `allow`, в котором не осталось стран, — тоже закрыто: все ходы получают отказ (как `required` без прокси), `pult doctor` — fail «все ходы запрещены…» с подсказкой и кодом 4,
  раздел окна — красная строка «Сейчас все ходы запрещены…».
- **`settings.set`** принимает ровно `{network: {guard: {mode, countries}}}` (рядом — `newSession`, `updates`). Под
  `network` ничего больше: прокси, профили провайдеров, `noProxy` окном не пишутся никогда. Разбор строгий
  (`parseGuardStrict`): лишнее поле, незнакомый или строчный код, пустой `allow` → `invalid_params`, файл не тронут.
  Пишется только `network.guard` (`writeNetworkGuard`): профили `network.<провайдер>` и всё прочее остаются в файле как
  были, а прежний верхний `guardCountries` (та же настройка, теперь перекрытая) удаляется в той же атомарной записи —
  предупреждение «есть оба» после первой записи из окна или `pult net guard` больше не звучит. Ключи — только
  собственные (`Object.keys`): `__proto__`/`constructor` под `network` и `guard` — лишние поля, отказ.
- **Сравнить-и-записать.** Окно шлёт `{network: {guard, expect}}`: `expect` — правило, на котором стоял черновик
  (`parseGuardShape`, пустой allow допустим). Не совпало с текущим — новый код `guard_changed` «правило стража изменилось
  снаружи (сейчас: …) — открой «Настройки» заново», файл не тронут; окно перечитывает настройки. `pult net guard`
  `expect` не шлёт: команда из терминала — осознанная перезапись. Плюс «Настройки» перечитывают `settings.get` при каждом
  открытии, и нетронутый черновик стража встаёт на свежее правило (секция пересоздаётся).
- **`deny` без стран** — страж выключен: пускается любая известная страна (неизвестная — нет). Допустимо; `doctor` —
  warn «страж выключен», окно — жёлтая строка «Страж выключен…». `settings.get` отдаёт `network: {guard, exits}` — `exits` это последний известный выход по
  провайдерам (`lastNetExits`, src/env/net.ts: `loc`, `path`, `reason`, `checkedAt`) из уже сделанных проверок, без
  новой пробы.
- **Сразу, без рестарта демона.** `settings.set` меняет `config.guard` (адаптеры читают его на каждой проверке) и зовёт
  `clearNetCache()`: кэш проверок (60 с) пуст, а поколение правил (`netGeneration`) сдвинуто. Адаптеры помнят поколение,
  при котором сессия последний раз ПРОШЛА стража (WeakMap по сессии), и проверяют выход перед ходом, если оно сменилось, —
  даже у тёплого процесса Claude и у Codex, которые без простоя стража не проходят. После отказа поколение не
  запоминается — следующий ход снова проверяется. Идущий ход не прерывается. Режим правила — и в ключе кэша.
- **Окно** («Настройки» ⌘, → «Страж сети», `NetGuardSection`, ui/src/model/netGuard.ts): радио «Запрещать страны из
  списка» / «Разрешать только страны из списка» (у каждого режима свой список: запретительный не становится
  разрешающим, возврат восстанавливает прежний — `switchGuardMode`); поиск по имени по-русски (`Intl.DisplayNames(['ru'],
  {type: 'region'})`, «ё» = «е») и по коду, чипы «Германия (DE) ×»; строки «claude: выход Германия (DE) — проходит / не
  проходит» ПОД ЧЕРНОВИКОМ правила (свежайшая проверка из `network.exits`, пунктов `net.*` доктора и событий
  `net.blocked`); предупреждение «С этими правилами сейчас ходы не пойдут: …» до сохранения (сохранить можно). «Проверить
  сеть» — `doctor.run {net: true}` (одновременные вызовы демон склеивает), кнопка гаснет на время проверки и ещё на
  15 с. Сам демон тоже не проверяет сеть доктором чаще раза в 15 с (`DOCTOR_NET_MIN_MS`, на провайдера): раньше —

## Ключи вопросов и модель угроз (0.3.7, окно 0.1.15 без замены)

Укрепление по отчёту в #13 (внешний вклад). Оболочка не менялась: окно и так вырезает `updatedInput` из `perm.resolve`
(`shell/src/contract.ts`) и ходит токеном хозяина.

**Модель угроз.** Демон и агенты работают от одного пользователя. Сокет `PULT_HOME/run/pultd.sock` (0600) и токен
`PULT_HOME/run/token` (0600) защищают от ДРУГИХ пользователей машины, не от кода самого владельца. До 0.3.7 держатель
токена мог всё: любой RPC, `perm.request` (право проверялось по самоназванию `client: 'mcp-ask'`), `perm.resolve` с
произвольным `updatedInput` (разрешить карточку `ls` и исполнить другую команду) и `scope: rule`; заглушка `pult mcp-ask`
читала токен хозяина с диска. Значит, агент, который прочёл файл токена (у Claude нет песочницы ОС — хватало инструмента
Read), получал весь пульт.

Достижимость (анализ 26.10.2026; «до» — 0.3.6, «после» — 0.3.7):

| кто | сокет | файл токена | до | после |
|---|---|---|---|---|
| Codex `read-only` / `workspace-write`, сеть выключена | `connect` отказан песочницей | читается | ничего | ничего |
| Codex с `sandbox_workspace_write.network_access = true` или `danger-full-access` | доступен | читается | всё | всё (остаточный риск; `pult doctor` предупреждает о сети) |
| Claude, инструменты Read/Edit (без песочницы ОС) | — | читается | всё | `deny Read/Edit(//PULT_HOME/run/**)` — отказ без вопроса |
| Claude, Bash `cat <run>/token` (даже при `Bash(cat:*)`) | — | — | всё | отказ без вопроса: Claude сверяет путь команды с deny (S12 T4) |
| Claude, разрешённый интерпретатор или `grep -r` по родителю run | доступен | читается | всё | всё (остаточный риск, S12 T4e, T5a) |
| Claude, Bash по правилу владельца (`Bash(python3:*)`) в «Только чтение» | доступен | читается | всё, без вопроса | `ask: ["Bash"]` — вопрос в Inbox |
| Claude, Bash после «да» в Inbox / в `full` | доступен | читается | всё | всё (остаточный риск) |
| заглушка `pult mcp-ask` | доступен | читала | токен хозяина | ключ вопросов: только `perm.request` своей сессии |
| держатель токена | доступен | — | всё, вкл. `perm.request` и подмену входа | всё, кроме `perm.request`; `updatedInput` — отказ |

**Что сделано.**

- **`perm.resolve`** — `'updatedInput' in params` → `invalid_params`, карточка ждёт дальше. Единственный законный автор
  `updatedInput` — брокер (ответы `AskUserQuestion` из `answers`); голое «да» возвращает исходный вход. В
  `permission.resolved.by` — `<client>#<connId>` ответившего соединения (`shell#3`, `cli#7`); карточка окна такой `by` не
  подписывает (`byHuman`, ui/src/components/PermCard.tsx), как и прежний `human`.
- **Ключи вопросов** (`src/perm/askKeys.ts`): `mint(session)` — 32 случайных байта hex, `lookup`, `revoke`; только в памяти
  демона, сверка `timingSafeEqual` по всем ключам без раннего выхода. Рукопожатие — ровно одно из двух: `{token}` → роль
  `owner`, `{ask}` → роль `ask` с привязанной сессией; оба сразу, чужой или снятый ключ — `bad_token`. Роль `ask`: любой
  метод, кроме `perm.request`, — новый код `forbidden`; `sessionId` — сессия ключа (другое имя — `forbidden`), ключ
  сверяется заново на каждом запросе (снятый посреди соединения — `forbidden`). Роль `owner`: `perm.request` — `forbidden`.
  Проверки `client !== 'mcp-ask'` больше нет: самоназвание прав не даёт (оно только в журнале и `by`, `[a-z][a-z0-9-]{0,31}`).
- **Адаптер Claude**: `writeMcpConfig` выдаёт ключ на каждый процесс `claude` и пишет его в env заглушки (`PULT_ASK_KEY`,
  рядом `PULT_HOME` — только ради пути к сокету, и `PULT_ASK_SESSION`); снимается на `exit`/`close` ЭТОГО процесса (рядом
  с удалением файла), на `close` сессии и `shutdown`. Заглушка (`src/perm/mcpAsk.ts`) токен не читает; нет ключа — отказ.
- **`--settings` каждой сессии Claude** (`claudeGuardPermissions` + `mergePermissions`, src/adapters/claude/argv.ts):
  всегда `deny: Read(//<run>/**), Edit(//<run>/**)` — путь как есть и по realpath, метасимволы глоба `[ ] { } ( ) * ?` и `\`
  экранированы `\` (`escapeRulePath`: без этого правило для папки `m[a]{b}(c)` не срабатывало, S12 T6); в `read-only` —
  `ask: ["Bash"]`. Правила О3 (браузер, только с брокером) сливаются в тот же один флаг. Правил `Grep(…)`/`Glob(…)` нет:
  в CLI 2.1.310 этих инструментов нет вовсе (system/init: `Bash`, `Read`; S12 T5b).
- **`pult doctor`** — пункт `codex.network` (src/env/codexConfig.ts) по `$CODEX_HOME/config.toml` или `~/.codex/config.toml`:
  warn «песочница Codex с сетью: агент сможет обратиться к демону Пульта», если `sandbox_workspace_write.network_access =
  true` (верхний уровень или выбранный `profile = "x"` → `[profiles.x.sandbox_workspace_write]`, профиль перекрывает) или
  профиль разрешений `default_permissions = "x"` открывает unix-сокеты (`[permissions.x.network]`: `unix_sockets`,
  `allow_unix_sockets`, `dangerously_allow_all_unix_sockets = true`). Файл только читается; разбор — маленький TOML без
  зависимостей (`parseTomlLite`: строки, многострочные `"""`/`'''`, массивы, вложенные и многострочные встроенные таблицы,
  массивы таблиц), так что текст строки или вложенная таблица за настройку не принимаются; кривой файл — warn «не разобран».
  Эффективный конфиг через `config/read` app-server доктор не спрашивает (лишний процесс codex на прогон). ok — «в режимах
  „Только чтение“, „Спрашивать“ и „Правки в папке без вопросов“ агент Codex не достанет сокет демона (в „Полном доступе“
  песочницы нет)». Тестовый демон и `PULT_TEST=1` читают `PULT_HOME/codex-config.toml`.
- **Ревью #16.** Рукопожатие: ключ сверяется, только если это ровно 64 строчных hex-знака (`isAskKeyShape`) — раньше
  `'é'.repeat(64)` (64 знака, 128 байт) доводил `timingSafeEqual` до броска в обработчике `data` сокета, и демон падал до
  рукопожатия; весь разбор hello теперь в `try` → `bad_token`. «Оба сразу» — по наличию полей (`{token: "", ask}` — тоже
  отказ). `askKeys.revokeSession(name)` — на `close` (`agent rm`) и `shutdown` адаптера: новая сессия с тем же именем
  старых ключей не получает. Бросок между выдачей ключа и спавном (`spawn` отказывает синхронно на нулевом байте в
  аргументе) снимает ключ и файл, сессия не остаётся «занятой», ход — `internal`. Самоназвание не по форме — `unknown`.
  Повторное ревью: `parseTomlLite` строит таблицы без прототипа (`Object.create(null)`) и отказывает ключам `__proto__`,
  `constructor`, `prototype` (файл — «не разобран»): `[__proto__]\napproval = "full"` в config.toml codex загрязнял
  Object.prototype в демоне (doctor.run идёт там), и `agent.start` без approval получал `full`, а `'updatedInput' in p`
  отказывал каждому `perm.resolve`. Вдобавок `dispatch` берёт параметры RPC в объект без прототипа (`ownParams`), а
  `perm.resolve` проверяет `Object.hasOwn(p, 'updatedInput')`. Полной защиты от загрязнения прототипа ВНУТРИ процесса нет и
  быть не может (обычные объекты менеджера тоже читают прототип) — поэтому закрыт источник, разбор чужого файла.

**Чего это не закрывает** (README, раздел «Безопасность»): код от того же пользователя (любая команда вне песочницы,

    (`APPLY_SHELLS_WAIT_MS`). Не переподключилось окно не из поставленного бандла — замены и перезапуска нет, отказ
    «закрой окно из …» в итог окна (иначе новое окно не взяло бы замок одного экземпляра, откат пометил бы годную
    версию bad);
  - `--expect` без сети — те же правила, что с сетью: только вперёд, не bad, не рабочая копия (иначе `--expect
    <previous>` тихо откатывал: у прежней версии тоже метка канала);
  - подготовку держит только идущая установка (`applying`), а не `failed` (залипал навсегда) и не ожидание ходов
    (бывает часами — к концу ходов версия уже готова); «Перезапустить» ждёт только ребёнка `--stage` (update.lock),
    окно, которое ещё качается, — нет: новый демон возьмёт его готовым или скачает сам;
  - «готово» в памяти сверяется с диском (`diskStaged`): израсходованное или убранное снова готовится; `stage` окна
    возвращает, подготовил ли он что-то (нечего — не «готово» и не провал); замена, сорвавшаяся до rename («закрой
    окно из …», окно не закрылось), возвращает новое окно из `.incoming` в `apps/ready-<v>` — повтор без загрузки;
  - `apps/ready-<v>/.sha256` — sha256 архива из подписанного манифеста; когда адрес архива известен, подготовленное
    берётся только с той же меткой (перевыложенный релиз с другим zip качается заново); без сети — любое той версии;
  - перезапуск окна — один за раз (как preflight замены), после lock снова проверяется «интерфейс старый?», другое
    открытое окно — отказ до сигнала;
  - `pult update` из терминала во время фоновой подготовки ждёт её (метка `run/update.lock.stage` с pid держателя, не
    дольше 10 мин, `STAGE_WAIT_MS`), а не отказывает «уже идёт другое обновление»;
  - плашка «перезапусти окно» скрывается своим ключом `stale:<версия>`: скрытый «Пульт X готов» её не прячет;
  - `release.mjs` сверяет `CFBundleShortVersionString` собранного (или поданного `--app-zip`, через `unzip -p`) окна с
    версией релиза.
  - Тесты: `update-checker` «ревью» (провал и ожидание ходов не держат подготовку, ждём только пакет, `stage → false`),
    «готово» сверено с диском; `apply-journal` (окна в журнале, ожидание `--stage` и отказ по сроку, чужой lock — сразу
    отказ); `update-channel` (без сети `--expect` на прежнюю — отказ); `app-update` «ревью» (подготовленное
    переживает сорванную замену, привязка к sha256, `stage → false`, один перезапуск на два нажатия, «уже
    перезапущено» после lock, другое окно и окно из журнала; демон: позднее hello окна — перезапуск, окно рабочей
    копии из журнала — отказ без bad); `ui/update` (ключ `stale:`); `release` (окно другой версии в zip — отказ).
