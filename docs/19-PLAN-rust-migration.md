# Переход Пульта на Rust и идеи из Herdr, bb, Delta и T3 Code

Обновлено 11.11.2026. Павел выбрал полный переход на Rust, включая демон, CLI и нативное окно.
R1 завершён как эксперимент, R2 и R3 выполняются. Переключение рабочей установки проходит отдельную приёмку R5.

Цель — перенести Пульт на Rust, сохранив рабочие разговоры, разрешения и пользовательские сценарии.
После переноса ядра выбрать Rust UI-стек по проверке реальных сценариев окна.
Польза оценивается по надёжности, расходу ресурсов и удобству разработки, а не по популярности языка.

## 1. Решение и альтернативы

Принятый путь — **Rust-демон и CLI → совместимость нынешнего окна → выбор Rust UI-стека → перенос окна**.
Каждый шаг заканчивается отдельным PR, зелёным CI и выполненной приёмкой. Не переписывать всё одним PR.

| Подход | Преимущество | Цена | Решение |
|---|---|---|---|
| Rust-ядро, нынешнее окно | Независимая проверка языка; UI продолжает работать | Временно два стека и совместимость протокола | Основной путь |
| Rust + React в другой оболочке | Можно сохранить React | Нужно заново проверить браузер Preview, доступность и системные интеграции | Рассмотреть на этапе окна |
| Всё на Rust/GPUI сразу | Нативный UI и единый основной язык | Одновременно меняются ядро, рендер, браузер и интеграции | Не начинать с этого |

Нынешний Пульт написан на TypeScript/Node.js, React и Electron. Swift не является заменяемым основным
стеком. Выбор Rust здесь — проверка системного языка на управлении процессами и состоянием.

Rust проверяет владение памятью при компиляции. Swift тоже обеспечивает безопасность памяти,
а Swift 6 language mode добавляет проверки гонок данных. Из этого не следует, что Rust лучше для
каждого приложения. Ни один язык не докажет правильность наших разрешений, отсутствие дублирующей
отправки или корректность восстановления разговора. Это проверяют модель состояний и испытания.

Источники: [Rust ownership](https://doc.rust-lang.org/book/ch04-01-what-is-ownership.html),
[Swift 6](https://www.swift.org/blog/announcing-swift-6/).

## 2. Границы переноса

```text
React UI / Electron shell ─┐
Rust CLI ─────────────────┼─ существующий RPC-контракт ─ Rust pultd
инструменты агентов ──────┘                                │
                                      сессии / журнал / разрешения
                                                          │
                                        адаптеры Claude / Codex / ZCode
```

На переходе TypeScript-адаптеры можно оставить в отдельном worker-процессе за версионированным
внутренним протоколом. Это временный мост, не второй владелец состояния. Rust-демон единолично
владеет журналом, сессиями, очередью и разрешениями. Worker только переводит протокол провайдера.
Новый и старый демоны никогда одновременно не управляют одной рабочей папкой данных.

Предлагаемый стек: stable Rust с закреплённым toolchain, Tokio для асинхронного IO,
Serde/serde_json для форматов, clap для CLI, tracing для диагностики. Зависимости и версии
закрепить после первого эксперимента; новые библиотеки добавлять под конкретную потребность.

Начальная структура — один Cargo workspace с библиотекой ядра и двумя бинарями `pultd`/`pult`.
Не дробить код на множество crates заранее. Внутри отделить чистые переходы состояний от IO,
адаптеры от продуктовых правил и OS-зависимые операции от общей логики.

Обязательные ограничения:

- Сохранить существующие CLI, коды выхода, RPC, идентификаторы и порядок событий либо выпустить
  явную версию протокола с проверенной совместимостью. Не считать общие типы доказательством совместимости.
- Сохранить все действующие режимы доступа, сетевые проверки, окружение дочерних процессов,
  персистентные правила и согласия. Права нельзя расширять из-за переноса.
- Сохранить RU/EN, историю, вложения, черновики, worktree, настройки и идентификаторы тредов провайдеров.
- Не менять одновременно язык и хранилище. Сначала поддержать нынешний формат журнала и файлов;
  SQLite рассматривать отдельным решением только при измеренной необходимости.
- Не менять публичное поведение «после аварии активный ход прерван» на обещание бесшовного продолжения.
  Сохранение живых процессов через рестарт — отдельная будущая функция.
- Собственный `unsafe` запрещён по умолчанию; необходимый FFI изолировать и описать отдельно.
  Это не означает, что зависимости или системные библиотеки не используют `unsafe`.

## 3. Этапы перехода

### R0. Контракт, исходные замеры и карта проверки

Ориентир: 3–5 рабочих сессий. До написания заменяющего демона.

1. Зафиксировать commit TypeScript-версии и собрать карту возможностей по README, реальным маршрутам,
   CLI, тестам и `docs/18-RUNTIME-VERIFICATION.md`. Отмечать расхождения документации с кодом.
2. Создать `verify-pult`: рецепты пользовательских сценариев, отдельный каталог данных и доказательства.
   Статусы: passed / failed / not run / blocked. Рецепт в карте не равен пройденной проверке.
3. Снять baseline на основном Mac: daemon-only и всё приложение раздельно; без агентов, с 1 и 10
   детерминированными процессами; короткая и большая история. CPU, память дерева процессов, запуск,
   RPC p50/p95, replay истории, размер поставки. Фиксировать ОС, железо и версии CLI.
4. Собрать обезличенный корпус событий Claude/Codex/ZCode и ожидаемые пользовательские результаты.
   Записи с токенами, приватными путями и содержимым проектов не публиковать.
5. Зафиксировать состояния и инварианты: принятая отправка, один владелец хода, момент сохранения,
   очередь, steer, разрешения, фоновые задачи, лимиты и прерывание.

Приёмка: baseline воспроизводится, у каждой существующей возможности есть владелец проверки;
все критические сценарии ниже имеют независимые ожидаемые результаты. Противоречия поведения
решаются явно: существующий баг не становится обязательным контрактом Rust-версии.

### R1. Ограниченный Rust-эксперимент

Ориентир: 3–5 сессий; после лимита времени остановиться и оценить результат.

Реализовать в экспериментальном каталоге: `pultd` с изолированным home/socket, handshake,
одна сессия Codex, поток событий, NDJSON-журнал, чтение после аварии и команда остановки.
Перед реальным CLI прогнать управляемый дочерний процесс. Без переноса UI и установки поверх рабочего Пульта.

Проверить kill до/после записи события, обрезанную последнюю строку, медленного читателя,
отмену, закрытие stdin/stdout, переполнение stderr и завершение дерева процессов.
Явно владеть `Child` и дождаться завершения; определить обработку process groups.
Tokio по умолчанию не убивает процесс при потере `Child`; одного `kill_on_drop` недостаточно
для договора о завершении всего дерева. [Документация](https://docs.rs/tokio/latest/tokio/process/index.html).

Приёмка: 100 циклов детерминированного сценария без потери подтверждённых событий,
зависших ожиданий и оставшихся дочерних процессов; один реальный Codex-сценарий.
Сравнение с Node по R0 и запись сложности разработки: время первой/повторной сборки,
сложности borrow checker, количество зависимостей и понятность ошибок.

Решение R1: продолжать, если проверки пройдены и нет необъяснённого ухудшения p95 более чем на 10%
в воспроизводимых замерах. Целевой сигнал пользы — хотя бы 25% снижения памяти daemon-only
либо другой измеримый выигрыш, обоснованный отдельным решением. Это предлагаемые пороги,
не обещание скорости. Если выигрыш только учебный, так и записать; не выдавать его за пользу продукту.

### R2. Единый контракт команд и основа Rust-демона

Ориентир: 1–2 недели после R1.

- Создать каталог методов с входами, выходами, ошибками, версиями и требуемыми правами.
  Из него получать схему, TS-типы клиента, справку и описание инструментов агентов.
- Добавить `pult --skill`: руководство именно установленной версии. Проверять покрытие команд
  и настроек тестом. Сгенерированные схемы не заменяют коротких примеров и ограничений.
- Перенести framing/RPC, авторизацию, lock единственного демона, конфигурацию, журнал,
  replay с курсором, ограниченные очереди и backpressure, подписки и диагностику.
- Определить подтверждение записи и crash recovery. После подтверждения запись должна
  переживать падение процесса; гарантию при потере питания отдельно обосновать fsync-политикой.
  Повреждение в середине журнала не игнорировать как допустимый обрезанный хвост.
- Для каждой команды запустить один набор контрактных сценариев против обоих демонов
  на разных временных home. Не отправлять одно живое задание сразу двум провайдерам.

Приёмка: нынешний клиент может подключиться к Rust-демону и читать fixture-историю;
неподдерживаемая версия отвергается понятной ошибкой; неподтверждённые операции не выдаются за успешные.

### R3. Сессии и адаптеры

Ориентир: 2–4 недели. Самый рискованный и изменчивый этап.

Сначала перенести реестр, начало хода, очередь, разрешения и восстановление. Затем адаптеры
по одному: Codex → Claude → ZCode. На время переноса остальных допустим worker-мост из раздела 2.

Переносить поведение по текущим `src/adapters/types.ts`, `src/sessions`, `src/perm`, а не по
названиям методов. Важны общий app-server у Codex, независимость его тредов, warm/resume у Claude,
вопросы посреди хода, отмена и поздние сообщения. Сохранять сырые ошибки провайдера для диагностики,
не записывать секреты в логи. Сверять корпус событий и реальные smoke-прогоны каждого адаптера.

Приёмка: каждый сценарий раздела 4 проходит для поддерживающих его провайдеров;
неподдерживаемая возможность явно объявлена. Worker удаляется только после паритета его адаптера.

### R4. Окно, CLI, Preview и системные интеграции

Ориентир: 1–3 недели.

- Перенести CLI на Rust без изменения пользовательских команд; сохранить CLI/SDK/UI на одном API.
- Подключить нынешний React/Electron к Rust-демону. Browser Preview остаётся в Electron;
  браузерные действия демона идут через существующую границу, а не запускают второй Chromium.
- Проверить MCP `pult_runtime`, control lease человека, iOS/Android, вложения и изображения,
  диктовку, уведомления, tray, deep links, автообновления и установщик.
- Перенести service install/doctor/update и сетевые профили; Node убирать из поставки только
  после инвентаризации оставшихся worker/MCP/служебных потребителей. Electron содержит собственный runtime.

Приёмка: существующие пользовательские e2e проходят против Rust-демона; окно закрывается без
остановки демона, и независимые ошибки вспомогательных сервисов имеют прежнюю область влияния.
Диктовка и браузер проверяются отдельно от демонных замеров памяти.

### R5. Переключение рабочей установки

Ориентир: 1–2 недели наблюдения после полного паритета.

1. Выпустить opt-in preview с отдельным home и явным выбором backend. Никакой тихой миграции.
2. Перед рабочим переключением остановить приём новых задач, завершить или явно прервать активные,
   остановить прежний демон и создать резервную копию данных. Проверить единственного владельца lock/socket.
3. Выполнить пробное чтение копии новым демоном; сравнить число сессий, историю, ссылки на вложения,
   правила, настройки и черновики. Не сбрасывать пользовательские согласия.
4. Семь дней повседневной работы на Rust и минимум 24 часа непрерывного стендового прогона
   с синтетическими процессами. Реальные платные ходы нужны только для ограниченных smoke-проверок.
5. Откат должен читать и новые записи Rust-периода. Пока это не доказано, не менять формат
   хранения. Возврат к старой резервной копии с потерей новых сообщений не считается безопасным откатом.

Приёмка: нет потери подтверждённых данных и необъяснённых отличий поведения; измерения R0/R1
повторены; рабочая установка и откат проверены. Затем удалить временный мост и TS backend.
Номер релиза выбрать перед выпуском; не связывать эту работу с устаревшими номерами фаз.

### R6. Выбор Rust UI-стека и перенос окна

После стабилизации ядра — отдельный эксперимент на 3–5 сессий для выбора Rust UI-стека.
Сравнить нынешнее окно с минимальным GPUI-клиентом: список сессий, длинный streaming-чат,
Markdown/код, ввод русского текста и один запрос разрешения.

Проверить выделение/копирование, IME, VoiceOver, клавиатуру, Retina, большие истории, память/CPU,
упаковку, обновления, встраивание браузера и передачу управления Preview. Не делать вывод о пригодности
GPUI по красивому статичному экрану. Если нужна иная веб-оболочка, сравнить её с теми же сценариями.

Приёмка решения: есть измерения, список обязательных системных мостов и стоимость их поддержки.
Выбранный Rust UI-стек переносится по экранам, с сохранением Electron до функционального
паритета. Решение Павла включает перенос React-интерфейса на Rust. Whisper и другие платформенные
помощники подключаются через явные границы интеграции.

## 4. Обязательные сценарии надёжности

| Область | Что должно быть доказано |
|---|---|
| Отправка | Повтор после сетевого обрыва не создаёт второй ход; неизвестный исход не маскируется успехом |
| Очередь | Порядок и выбранный Send now сохранены; steer доходит в свой ход или возвращается в черновик |
| Вопросы | Синхронные/асинхронные формы, поздний ответ, переключение чата и восстановление черновика |
| Разрешения | deny по умолчанию, смерть отправителя, отзыв правила; запрос одной сессии не одобряет другую |
| Параллельность | Остановка одного треда Codex не гасит общий app-server и чужие задачи |
| Завершение | drain stdout/stderr, таймауты, отмена, process groups, отсутствие zombie/orphan в оговорённых случаях |
| Диск | Нет места, запрет записи, обрезанный хвост, ошибка fsync, атомарная замена файлов, lock |
| Восстановление | Падение до/после acknowledgement, cursor replay, медленный UI, повторная подписка |
| Защита | Сетевой guard, режимы доступа и env allowlist не обходятся новым runtime |
| Данные | Unicode, большие истории/вложения, относительные пути, symlink, старые настройки |
| Устройства | Take control блокирует следующую команду агента; reconnect не оставляет вечную аренду |
| Обновление | Несовместимые клиент/демон распознаются; откат сохраняет сообщения после перехода |

Гарантии Rust в памяти не покрывают эти сценарии. Даже компилируемая программа может зависнуть,
перепутать треды или дважды выполнить внешнюю команду. В частности, exactly-once исполнение после
аварии возможно обещать только при поддержке дедупликации внешней стороной; иначе нужен статус
неизвестного результата и явное восстановление без слепого повтора.

### Новый чат и выбор модели по результатам изучения bb

Первый UI-шаг — общее меню провайдера, модели, усилия и Fast с поиском.
Выбор модели сохраняет меню открытым для остальных настроек. Клавиатурная навигация,
Escape, управление фокусом и текущие горячие клавиши входят в приёмку.

Следом — запланированные пресеты нового чата. Они сохраняют модель и усилие отдельно
для каждого провайдера и дают быстрый повторный выбор конфигурации. Нынешний приоритет
`newSession.defaults` закреплён в `docs/DEV.md` и тестах шага B. Память выбора подключается
через миграцию к пресетам шага C с проверкой старых настроек и явных изменений человека.

Меню проекта получает поиск по всему списку известных проектов и недавних папок.
Результат учитывает элементы за пределами нынешних первых 12. Создание чата без проекта,
системный выбор папки и сохранение черновика входят в приёмку вместе с поиском.

Изменения проверяются в нынешнем окне и становятся обязательными сценариями переноса R6.
Приёмка включает обе темы, узкое окно, длинный каталог моделей, смену провайдера,
возврат к черновику, отправку с выбранной конфигурацией и управление клавиатурой.

### Общая память агентов: отдельный продуктовый шаг M

В bb реализован отдельный плагин: SQLite/FTS5, области проекта и global, короткий каталог
в контексте, чтение подробностей по запросу. Изменения проверяют ожидаемую версию записи,
сохраняют историю и источник. Каталог обновляется к следующему ходу. Это полезный образец
для локального Пульта; детали интерфейса доступа у нас будут собственными.

Порядок реализации после устойчивого контракта контекста R3:

1. **M1 — хранилище и API.** Отдельная SQLite-база новой функции; формат нынешних сессий и
   NDJSON-журнала остаётся прежним. Запись содержит ID, область, projectId, название, краткое
   описание, подробности, источник session/event, автора, причину, версию, признак закрепления и даты.
   Запись и её история обновляются одной транзакцией. Update/delete требуют `expectedVersion`;
   конфликт возвращает текущую версию и требует повторного чтения. Все изменения используют
   commandId/receipts R3: повтор add после обрыва возвращает ту же запись. Удаление по умолчанию мягкое.
2. **M2 — доступ всех агентов.** Одинаковые list/search/get/add/update/forget для CLI и MCP,
   общий backend с UI. В начале каждого хода — ограниченный каталог с ID и краткими описаниями;
   подробности выдаются через поиск и get. Начальный предел каталога — 4000 символов с
   дополнительным ограничением байтов. При переполнении — приоритет закреплённых записей и
   явное указание доступного поиска. Первый поиск — полнотекстовый FTS5; embeddings добавлять
   только после измерения качества. Запись становится видна на следующем ходу или при явном чтении.
3. **M3 — управление человеком.** Раздел «Память»: область, поиск, источник, редактирование,
   история версий, закрепление, удаление. Окончательное удаление очищает запись, её историю,
   FTS-индекс, payload receipts и кэш каталога; уже переданный провайдеру контекст не отзывается.
   Автоматическое сохранение сначала предлагает заметку с источником; фоновое обобщение и
   дедупликация проходят отдельную приёмку после ручного MVP.

Область по умолчанию — проект, global выбирается явно. У worktree и основной папки один
projectId; идентичность Git-проекта учитывает общий git-dir worktrees, а не только
`--show-toplevel`. Для папок без Git — канонический путь. Перенос проекта требует явного
сопоставления прежней идентичности, без случайного объединения разных репозиториев. Агент получает текущий проект и global, чат без проекта — только
global. Область проверяет сервер из доверенного контекста сессии, а не из произвольного
аргумента агента. Человек видит все области через отдельный owner API.
В чате можно отключить чтение и запись памяти; временный/приватный режим, если поддержан,
по умолчанию работает с выключенной памятью.

В память сохраняются подтверждённые устойчивые факты и решения с источником. Содержимое
считается данными, не повышает разрешения и не перекрывает инструкции. Проверка секретов и
подозрительных инструкций — дополнительный фильтр; она не гарантирует обнаружение всего.
Существующую память провайдеров нельзя автоматически импортировать или отключать.

Приёмка M: Claude сохраняет факт → Codex читает ту же версию; конкурентная запись даёт
конфликт; повтор add возвращает прежнюю запись; выключенная память не читается и не пишется;
другой проект не получает данные; worktree разделяют память; после рестарта записи
доступны; удалённое исключено из поиска и нового контекста; предел каталога соблюдается;
ошибка памяти имеет понятную диагностику и не приводит к повторной отправке сообщения.

## 6. Рабочий процесс и оценки

Каждый этап: ветка → небольшой PR → релевантные проверки → CI → squash merge. Перед первым коммитом
сверить личный email автора. Существующие незакоммиченные изменения UI не включать в миграционные PR.
Первую реализацию вести в отдельном worktree; референсные репозитории не запускать с их install-скриптами.

CI Rust: format, clippy с запретом предупреждений, unit/contract/integration, сборка macOS arm64 и Linux,
проверка схем/руководства и зависимостей/лицензий. Свои lifecycle-тесты гонять реальными управляемыми
процессами. Политики тестировать без IO; интеграции — на реальных границах. Не копировать подход bb
«без комментариев»: причины решений, ограничения и опасные места в Пульте документировать.

Для агента проверки сделать discoverable-командой; ошибка обязательной проверки должна останавливать
CI. Локальные pre-commit/agent hooks могут запускать быстрый format/schema-check, но не заменяют CI,
не чинят файлы скрытно и не запускают платные модельные smoke-прогоны автоматически.

Резерв предварительной оценки: **8–14 недель при регулярной работе до переключения ядра**;
при освоении Rust — больше. Сумма ориентиров R0–R5 не является сроком выпуска. После R1 пересчитать
по фактической скорости переноса и инвентарю R0. Нативное окно, P1–P6 и новые провайдеры сюда не входят.
При нехватке времени сначала откладывать нативное окно и продуктовые дополнения; не сокращать
проверки данных, разрешений и отката. Если эксперимент не подтвердит пользу, его можно оставить
учебным результатом без остановки развития нынешнего Пульта.

Replay и новые события используют durable-курсор и уведомление о последнем записанном ID.
Договор, пределы памяти и live-reset пустого набора сессий описаны в
`docs/rust/R2-SUBSCRIPTIONS.md`. Каталог содержит 7 реализованных методов.

Далее переносятся снимок и история для окна, восстановление срезов сессий и реестр сессий.
Фактические фазы и работа провайдеров проходят свою приёмку при переносе исполнения.

### Управление CLI из окна

Панель управления использует host-local bridge для старта, остановки и перезапуска демона,
офлайн-диагностики и обслуживания Claude/Codex. Эти операции работают и без RPC-соединения
с демоном. Их типизированные интерфейсы и договор `docs/20-CLI-CONTROLS.md` входят в объём
переноса оболочки R6. При переносе сохранить явное подтверждение, выбранную установку CLI,
сетевой профиль, секреты в main-процессе и штатную интерактивную авторизацию провайдера.


### Продолжение R2 — снимок и история окна

Rust реализует `events.snapshot`, `events.history` и `events.get`: 10 методов из 86.
Снимок и исходные события используют общий журнал, история — файл отдельной сессии,
как в Node. Сохранены уплотнение дельт, страницы по границам ходов, ограничения ответа,
UTF-16 и кэш четырёх недавно использованных сессий с инвалидированием по файлу.
Договор — `docs/rust/R2-HISTORY.md`.

Автопересборка файлов сессий отложена до явной обработки конфликтов: внешняя перезапись
сейчас является поддержанным источником истории и не должна молча теряться. Следующий
шаг — реестр сессий: формат и миграции, восстановление статусов, очередь и внимание.
Провайдеры, live-фазы и переключение рабочего окна остаются следующими этапами.


### Продолжение R3 — реестр и восстановление сессий

Rust читает и атомарно сохраняет реестр, мигрирует прежние уровни доступа с первой
backup-копией и маркером, восстанавливает статусы, отметки прочтения и начало последнего
хода. Принятые реплики удаляются из очереди по подтверждениям общего журнала и файла сессии,
остальная очередь ставится на паузу. Добавлены `agent.rename`, `agent.archive` и `agent.seen`.
Каталог содержит 13 реализованных методов. Договор находится в `docs/rust/R3-REGISTRY.md`.

Следующий шаг переносит менеджер исполнения сессий, начало хода, очередь и разрешения.
Адаптеры подключаются по очереди Codex → Claude → ZCode. `agent.list` проходит приёмку
вместе с фактическими полями доступа, внимания и фаз. Грамматика старых дат V8 пока
поддержана частично, неизвестная дата маркера миграции даёт явную ошибку.


### Продолжение R3 — чтение результатов и дерева

Переносятся `agent.read` и `agent.tree`: общий журнал, курсоры и страницы JSON,
текст завершённых сообщений, worktree и иерархия инструментов/субагентов.
Контракт CLI сохраняет NDJSON для read и текст/JSON для tree; RU/EN проверяются отдельно.
Договор и сценарии совместимости находятся в `docs/rust/R3-QUERIES.md`.
После приёмки каталог содержит 15 методов. Исполнение, ожидание хода и usage пока не перенесены.


### M1 — основа общей памяти

Реализованы SQLite/FTS5-хранилище и семь owner-only методов памяти с CLI: версии,
история, атомарные receipts, мягкое удаление и изоляция областей. Git-проекты и worktree
получают общую идентичность. Повреждённая база отключает память с диагностикой, сохраняя
остальные функции демона. Договор — `docs/rust/M1-MEMORY.md`.

Это новая функция: поддерживаемых Rust-методов становится 22 из 93, но перенос прежнего
контракта остаётся 15 из 86. M2 должен привязать проект к доверенной сессии агента,
подключить ограниченный каталог к ходам и чтение/запись через CLI/MCP. Затем M3 — окно
управления памятью и окончательное удаление, включая payload receipts. До M2 записи
создаёт owner API; реальный обмен знаниями между ходами Claude/Codex ещё не включён.


### M2 — ограниченное чтение памяти доверенной сессии

Добавлены owner-регистрация контекста, выдача и отзыв read-only ключей, статус и
ограниченный каталог памяти. Проект закрепляется при bind; каждый запрос проверяет
актуальную сессию и полномочия. General получает только global. CLI с PULT_MEMORY_KEY
не читает owner token/config и не возвращается к owner при ошибке. Архивация, rebind,
ротация и перезапуск инвалидируют ключи. Договор — `docs/rust/M2-READ-CONTEXT.md`.

Поддерживаются 27 методов из 98: перенос прежнего контракта остаётся 15 из 86,
остальные 12 — новые методы памяти. Это завершённый read-only срез M2; автоматический
каталог в ходе, запуск провайдера с ключом, запись агентами и MCP ещё не включены.
Следующий шаг — менеджер исполнения R3 и доверенные настройки хода, затем выдача ключа
провайдеру и подключение памяти. M3 с UI и физическим удалением остаётся в плане.


### Продолжение R3 — ядро управления ходом

Добавлены типизированный снимок настроек и внутренняя машина состояний хода. Она
бронирует имя сессии до ожиданий, разделяет начало и завершение, сохраняет бронь при
отмене до подтверждения остановки и отбрасывает callbacks старого запуска/экземпляра.
Результаты и активные ходы ограничены по памяти. Неизвестный inherit не считается
автоматически более широким, чем ask. Договор — `docs/rust/R3-TURN-COORDINATOR.md`.

Это внутренний срез: RPC и каталог остаются 27/98, перенос прежнего API — 15/86.
Тестовый driver проверяет порядок событий через управляемые барьеры; настоящий
worker, durable receipts, consent/access gate, очередь, broker и lifecycle провайдеров
ещё нужно соединить с ядром. Следующий шаг — эта интеграция, затем Codex и память в ходе.
