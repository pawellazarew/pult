# Спайк: ZCode как третий провайдер

Статус: спайк завершён 29.10.2026 (все замеры — на живом CLI, версия 0.17.0, машина владельца).
Вопрос спайка: можно ли гонять `zcode` как фонового агента Пульта теми же двумя дорогами, что
`claude` и `codex`, и что для этого нужно. Ответ: да; рекомендуемый первый маршрут — процесс на ход
(как у claude), полный разбор app-server — вторым этапом.

## Что за CLI

ZCode — CLI-агент от Z.AI (семейство GLM). В поставке десктоп-приложения ZCode.app бинаря в PATH
нет: рантайм лежит в `/Applications/ZCode.app/Contents/Resources/glm/zcode.cjs` и запускается как
`node zcode.cjs …`. Грабля та же, что у codex в ChatGPT.app (обновление приложения двигает путь):
адаптеру нужен поиск по известным путям + симлинк `~/.local/bin/zcode`, как `codex`.

Вход в аккаунт — `zcode login` (браузерное OAuth; общие креды с десктоп-приложением, хранятся вне
`PULT_HOME`). Пульт, как и с claude/codex, сам логинить не умеет и не должен.

## Маршрут A: процесс на ход (`-p`), как адаптер claude — ГОТОВ НА 90%

Замерено на живом CLI 29.10.2026 (временные git-папки, ходы по одному сообщению):

- **Headless-ход**: `zcode.cjs -p "<текст>" --cwd <папка> --mode <режим> --surface terminal --json`.
  Ход реально работает: создавал файл, отвечал текстом, exit 0. `--surface terminal` обязателен —
  иначе CLI считает себя десктопом.
- **Машинный вывод — `--json`, ОДИН итоговый JSON на stdout**: `sessionId` (`sess_…`), `turnId`
  (`turn_…`), `response` (итоговый текст), `usage` (input/output/cache/reasoning токены,
  счётчик запросов модели), `projection` (`contextUsed`/`contextWindow` — контекст сессии готов
  бесплатно, у claude это отдельное событие), `eventCount`. Это удобнее claude stream-json: без
  потокового разбора, но нет и промежуточных событий (см. ограничения).
- **Возобновление**: `--resume <sessionId>` — ИЗМЕРЕНО: число, заданное в первом ходе, воспроизведено
  во втором процессе; `sessionId` сохраняется, `turnId` новый. Ровно модель claude-адаптера
  (`--resume <uuid>`, `providerSessionId` в реестре по первому ходу).
- **Режимы разрешений** `--mode`: `plan` (замерено: файл не создан, модель ответила планом — честный
  read-only), `edit`, `build`, `yolo`, `guarded` (замерено: безопасная команда `touch` выполнена без
  вопроса; эскалации в headless спросить некому). Предварительное соответствие режимам Пульта:
  `read-only → plan`, `workspace → edit`, `full → yolo`, `ask → guarded` (уточнить семантику build
  и guarded при адаптере; ask без живого вопроса = маршрут B).
- **Модель/усилие**: флаги `--model*` в CLI есть (семейство GLM-4.6/4.5/Air/Flash); список моделей
  для меню окна снять при адаптере.
- **Прочее**: `--disallowed-tools` — точечно выключать инструменты (аналог нашего запрета Read/Edit
  на `~/.pult/run`), `--cwd`, `--attach` (файлы в реплику).

Ограничения маршрута A: нет потоковых событий хода (лента оживёт только после конца хода), нет
промежуточного вывода инструментов в журнал, разрешения не доходят до Inbox (нужен режим без
вопросов), нет прерывания хода сигналом по смыслу (SIGTERM убивает процесс — как у claude до M8),
живая строка «что делает сейчас» невозможна.

## Маршрут B: один `zcode app-server` на всех, как адаптер codex — ВТОРЫМ ЭТАПОМ

`zcode.cjs app-server` поднимает stdio-сервер «ZCode Protocol». Имена из бандла (zod-схемы в
`zcode.cjs`):

- методы `session/*`: `create`, `send`, `resume`, `close`, `stop`, `subscribe`, `events`, `read`,
  `messages`, `list`, `fork`, `compact`, `usage`, `subagents`, `setMode`, `setModel`,
  `setThoughtLevel` (живая смена режима/модели/усилия — лучше, чем у codex), `goal`,
  `requestRuntimePreferences`;
- события: `permission.requested` / `permission.resolved` (провод вопросов до Inbox), строки
  `session-always-allow` («всегда разрешать» — аналог codex-правил), `session.closed`,
  `session.conflict`, `session-context`;
- конверт — НЕ JSON-RPC: строки `{"method","params"}` без `id`/`jsonrpc` (zod их отвергает с
  `unrecognized_keys`), сервер сам шлёт уведомления `startup/storageState` до первого запроса.
  Рукопожатие в спайке НЕ подобрано (сервер молчит) — разбор конверта и схемы это работа адаптера:
  всё валидируется zod, схемы читаются из бандла.

Маршрут B даёт: Inbox-разрешения, live-события и фазы, `setMode` на живую, usage на ходу.

## План адаптера (предложение)

1. **Z1 (маршрут A):** адаптер `src/adapters/zcode/` по образцу claude: спавн `node <bin> -p …
   --json`, разбор итогового JSON в `mapper`, `providerSessionId` по первому ходу, resume вторым
   процессом. Режимы: `plan/edit/yolo/guarded`; модель — через `--model`. Страж сети и автоназвание —
   как у claude (последнее только если у Z.AI есть дешёвая модель; иначе выключено). Поиск бинаря:
   известные пути ZCode.app + `ZCODE_BIN` + симлинк. Окно: третий пункт в «+ Сессия», метка «ZCode».
2. **Z2 (маршрут B):** разбор app-server-конверта (схемы zod из бандла), один процесс на всех,
   провод `permission.requested` в брокер, live-фазы через `session/events`. Заменяет A для новых
   сессий, как codex-адаптер не мешает claude-маршруту.
3. **Z3:** `pult doctor` — проверка бинаря/логина zcode; фикстуры живых прогонов как
   `test/fixtures/zcode/` (записыватор по образцу `record-claude-fixtures.mjs`).

Риски: путь бинаря плывёт за обновлениями ZCode.app (грабля codex повторяется); протокол app-server
недокументирован и может меняться (у codex так же); санкционная логика Z.AI неизвестна — страж
страны выхода оставить включённым для zcode по умолчанию.
